# v0.3.0: reach (MCP)

Status: **design**, on branch `release/v0.3.0` (started 2026-09-30). Open questions are in §8; the owner answers them one at a time before any code.

v0.3 brings Grounded to the tools people already use, through the Model Context Protocol, in both directions: **Grounded as an MCP server** (other AI tools search its knowledge bases and ask its agents) and **an MCP client inside agents** (agents call tools from admin-approved MCP servers). It adds stored health for models and MCP servers, and OpenTelemetry tracing across answers and tool calls. Roadmap items C1, E11 and F1. The Teams/Slack bot (D1) is not in v0.3 (owner, 2026-09-30).

Every feature is optional and off until a platform admin turns it on.

---

## 1. Exit criteria

1. **Server:** an MCP client (for example an agent harness such as OpenCode or Pi, or any client that speaks MCP over Streamable HTTP) connects to Grounded with an API key, lists the knowledge bases and agents that key may use, searches a knowledge base and asks an agent, and gets passages or answers with citations and claim verdicts. Classification ceilings, query limits, budgets and the audit log apply exactly as they do to the REST API.
2. **Client:** a platform admin registers a remote MCP server, approves some of its tools and sets a classification ceiling; an editor enables approved tools on an agent; the agent calls them during an answer; the calls are audited, metered and shown in the answer, and a tool can never receive data above its ceiling.
3. **Health:** Admin → Models and Admin → MCP servers show the last test result and time for each model, connection and MCP server, re-tested on a schedule; failures appear under Needs attention.
4. **Tracing:** with an OpenTelemetry endpoint configured, one answer is one trace across HTTP, retrieval, model calls, SystemOne and MCP tool calls, and trace context flows through MCP `_meta` as the spec describes.
5. The usual gates: OpenAPI first, the authorization matrix, tests and E2E with axe, lint limits, CI green, a walkthrough by role, `v0.3.0-rc.1` on the reference install before `v0.3.0`.

## 2. Which MCP

- **Protocol revision `2026-07-28`** (the current one): stateless (no sessions, no `initialize` handshake; the protocol version and client capabilities travel in each request's `_meta`), `server/discover`, the Streamable HTTP transport with the required `Mcp-Method`/`Mcp-Name` headers, cacheable list results (`ttlMs`, `cacheScope`), `resultType` on every result.
- **Older clients:** the official Go SDK (`github.com/modelcontextprotocol/go-sdk`, v1.7.0 or later) also serves `2025-11-25`, `2025-06-18`, `2025-03-26` and `2024-11-05` clients, so clients that haven't caught up still work.
- **Not used:** the deprecated Roots, Sampling and Logging features; the deprecated HTTP+SSE transport; local stdio servers (Grounded runs on a server; it never starts processes for MCP).

## 3. Grounded as an MCP server (C1a)

- **Endpoint:** `POST /mcp` on the API (Streamable HTTP). Off until a platform admin turns it on (Admin → Overview → Features gains "MCP server"). Disabled per team is possible through the key's scopes.
- **Who connects:** API keys (personal and service), as `Authorization: Bearer …`, with a new scope `mcp` (added to the key's scopes like `retrieve` and `chat`). The key's own limits apply: its KB list, its team, its owner's current role.
- **OAuth (experimental, off by default):** a platform setting turns on Grounded as an OAuth 2.1 authorization server for `/mcp`: `/.well-known/oauth-protected-resource` and `/.well-known/oauth-authorization-server`, Client ID Metadata Documents (and Dynamic Client Registration for older clients), PKCE, an `iss` in authorization responses (RFC 9207), sign-in delegated to the platform's OIDC provider, a consent screen naming the client and what it may use, and short-lived access tokens bound to the `/mcp` resource (RFC 8707) that act as the signed-in person with the `mcp` scope. Revocable from the person's API keys page. Audited.
- **Tools** (deterministic order, cacheable lists):
  - `search` — arguments: `knowledge_base` (an enum of the KBs the key may search), `query`, optional `top_k` and filters. Returns passages with title, heading path, URL and a citation number; structured content carries the same as JSON.
  - `ask` — arguments: `agent` (an enum of the agents the key may chat with), `question`, optional `conversation` handle for follow-ups (a server-minted handle, since the protocol is stateless). Returns the answer text with `[n]` markers, the citations, and the claims with verdicts when SystemOne checks are on.
- **Resources** (optional in v0.3): each KB's documents as read-only resources (`grounded://team/kb/document`), so a client can open a cited document. Behind the same permissions.
- **Everything else as today:** classification (an agent's audience and model ceilings), query limits per key, budgets (429 → an MCP tool error with the reason), usage recorded with channel `mcp`, audit entries (`mcp.search`, `mcp.ask`), moderation for public agents (not reachable over MCP: public agents are for anonymous people, MCP needs a key).
- **Docs:** a page per popular client with its configuration snippet (Streamable HTTP URL and header).

## 4. MCP client in agents (C1b)

- **Registry** (Admin → Models → **MCP servers**, platform admins): a remote server's name, URL (https only), authentication (a static header such as `Authorization: Bearer …` or a vendor's API-key header, stored encrypted like connection keys; no OAuth to outside servers in v0.3), a **classification ceiling** (the highest data level it may receive), a timeout, and the list of its tools fetched from the server, each **approved** or not. Tool descriptions from the server are shown to the admin before approval (they are prompts the model will read).
- **Per agent** (Build → a new **Tools** section, editors): choose approved tools. An agent whose data is above a server's ceiling can't enable its tools (checked again at publish and at every call, as with models).
- **At answer time:** approved tools join `search_knowledge` in the agent loop (`internal/agentloop`: an MCP tool is an `agentloop.Tool` whose `Execute` calls the server). Calls are bounded (timeout, result size, calls per answer), run under the team's limits, metered (a new ledger kind `mcp_calls`, priced per call if the admin sets a price), and audited with the tool, the server and the result size (not the content).
- **Untrusted output:** a tool's result is untrusted text: it's wrapped as data (never instructions), screened by SystemOne's passage checks when they're on, and cited as a source ("From the Weather tool") so answers stay grounded; §8 Q4.
- **What's sent:** only the arguments the model chose, never the conversation or passages unless the model puts them in an argument; the classification ceiling is the guard. MRTR input requests from a server (the new pattern for elicitation) are refused in v0.3: an agent answering a person can't ask a remote server's questions.

## 5. Stored health (E11)

A `health_checks` table (subject: model, connection or MCP server; status; latency; error class; checked at). The existing Test buttons store their result; a River periodic job re-tests enabled subjects every 15 minutes (with jitter and a per-connection limit). Admin → Models / Connections / MCP servers show "Healthy · 3 min ago" or the error; failures appear on the admin Overview under Needs attention; a metric and an alert rule for dashboards. SystemOne connections use the SystemOne probe fixed in v0.2.2.

## 6. Tracing (F1)

OpenTelemetry for Go: spans for HTTP requests, retrieval (vector, lexical, fusion), model calls (with token counts, not content), SystemOne judging, MCP tool calls (client) and MCP requests (server), River jobs. W3C trace context in and out, including MCP `_meta` (`traceparent`, `tracestate`). Off unless `OTEL_EXPORTER_OTLP_ENDPOINT` is set; sampling configurable. The reference install sends to its existing observability stack; the docs show Tempo/Jaeger.

## 7. Data and API

Migration (next number): `mcp_servers`, `mcp_server_tools` (approval), `agent_tools` (per agent version), `health_checks`, the `mcp` API-key scope, the `mcp_calls` ledger kind. API (OpenAPI first): admin CRUD for MCP servers and tool approval, a refresh of a server's tool list, agent version fields for tools, health read endpoints; `/mcp` itself is described in the docs, not the OpenAPI (it's JSON-RPC). All in the authorization matrix.

## 8. Open questions

1. ~~MCP server sign-in?~~ **API keys, plus experimental OAuth behind a platform setting, off by default** (owner, 2026-09-30). OAuth is where it's headed: Grounded acts as an OAuth 2.1 authorization server for `/mcp` in front of the platform's OIDC provider (protected resource metadata, Client ID Metadata Documents, with Dynamic Client Registration for older clients, a consent screen, short-lived tokens bound to the resource), marked experimental until clients and the spec settle.
2. ~~Server tools?~~ **Two generic tools, `search` and `ask`** (owner, 2026-09-30), each with an enum of what the caller may use; their descriptions list each option's name and one-line description.
3. ~~Client authentication to outside servers?~~ **Static credentials only in v0.3** (owner, 2026-09-30): a header stored encrypted like connection keys. OAuth to outside servers follows once the Go SDK's client OAuth is no longer experimental.
4. Tool results in answers: cited as sources like passages, or used as context only?
5. Tracing (F1) in v0.3, or later?
