# Grounded v0.5.0

v0.5.0 is the first release of "better knowledge in". It lets a platform admin **try new indexing settings on a knowledge base and see what changes before anything switches**, and it adds an **opt-in chunker** that leaves fewer, fuller passages. It also fixes a screen-reader problem in every picker, a menu that closed itself while a list reloaded, and a delay in cleaning up after a discarded migration.

**What is not in this release.** The roadmap's v0.5.0 also named parent/child retrieval, contextual chunks, tables kept structured, fuzzy boilerplate matching and a content health report. They are not here, on purpose: each is large, and each changes what is indexed, which is exactly what the index preview exists to judge. Building them first and previewing them after is the better order, so they follow in later releases. Splitting a section that mixes procedures (C15) also waits: it needs real example pages.

## Highlights

- **Index preview.** **Admin → Embedding profiles → Migrations → Preview new settings…** builds a new index of a knowledge base with changed settings (passage size and overlap, embedding model, prefixes, chunker) **beside the current one**. The knowledge base keeps answering from the current index the whole time. When the new index is built, the platform runs the knowledge base's evaluation sets on both, retrieval only, and the migration's page shows what got better and what got worse: recall, MRR, questions ranked first, and how many questions improved, got worse or stayed. Then you **Switch to the new index** (the same atomic switch as a migration, with the old vectors kept for the grace period so you can switch back) or **Discard preview**. Evaluation sets belong to the team, so the platform admin sees the scores and counts without the questions; the team's editors see each question that changed, with its rank on both indexes, on the knowledge base's own page. The preview's runs are not in the team's run list, trend or regression checks. See [`operations/profile-migration.md`](../operations/profile-migration.md).
- **Chunker v2, opt-in.** A profile has a chunker version. Version 1, the original, is unchanged and is what every profile uses. **Version 2 merges short neighbouring sections** into one passage (when the passage and the next section are both under a quarter of the passage size, under the same parent heading and on the same page) and **drops passages that are only a heading and a rule**. On the documentation pages tried it left the same text in the same order with fewer passages (counting words in place of tokens: one page went from 17 passages to 13 at a size of 512, and a generated document of many short sections from 181 to 48; pages whose sections are already near a passage's size do not change). **It has not been measured on a real knowledge base with a real embedding model, so this release does not say it retrieves better.** Try it with the index preview on a knowledge base that has evaluation sets, and decide by the numbers. A profile chooses its chunker when it is created (**Add profile → Chunker**, or `chunkerVersion` in the API); a preview can change only the chunker.
- **Every list of options has an accessible name.** The option list of a picker (the team picker, the model selector, comboboxes) was announced as an unnamed list. Each now has a name ("Teams", the field's label, or the placeholder), which also fixes an accessibility check that failed intermittently in the project's own tests.
- **The Conversations list keeps its rows while a search loads.** Changing the search, agent or date range replaced the list with a loading placeholder, which also closed a row's open actions menu. The previous rows now stay until the new list arrives.
- **Cleaning up after a discarded migration starts at once.** The request to delete a cancelled migration's vectors, or a switched-back migration's, could be dropped when a cleanup run had just finished, leaving the vectors until the next periodic run, up to ten minutes later. It is no longer dropped.
- **PostgreSQL 18.** A delete that a foreign key blocks (a model used by a profile, a connection with models, and the like) now says it is in use on PostgreSQL 18 as well as 17. The reference install stays on 17.

## Upgrading from v0.4.4

A rolling upgrade with no downtime. Take a backup as for any upgrade ([`operations/upgrades.md`](../operations/upgrades.md)), then change every `?ref=v0.4.4` in your overlay to `?ref=v0.5.0` and pin the new digests of `ghcr.io/ncecere/grounded` and, if you run it, `ghcr.io/ncecere/grounded-ocr`.

- **Three migrations** (the schema moves from version 45 to 48), all additive and quick: `00046` adds `profile_migrations.hold` and the `ready` status, `00047` adds `embedding_profiles.candidate_of`, `00048` allows the `index_preview` evaluation trigger. Nothing is rewritten and nothing needs configuring. The previous release keeps working against them during the roll: it never creates a held migration or a candidate profile.
- **No new environment variables.**
- **Before rolling back to an earlier release,** switch or discard any index preview: an earlier release does not know hidden candidate profiles and would list one, and could not act on a migration that is ready to switch.
- **API (all additive):** `POST /v1/admin/profile-migrations` takes `hold`; migrations gain the status `ready` and the fields `hold` and `canSwitch`; new `POST /v1/admin/profile-migrations/preview`, `POST …/{id}/switch`, `POST …/{id}/evaluate` and `GET …/{id}/preview`, and `GET /v1/teams/{team}/kbs/{kbId}/index-preview`; `EmbeddingProfile` gains `candidateOf` and profile creation takes `chunkerVersion` (an unknown version is `400 invalid_chunker_version`). Platform admins get a notification when a preview is ready, and the audit log records `kb.profile_preview_ready`, `kb.profile_preview_evaluate` and a held start.

## Known limitations

The [v0.4.4 limitations](v0.4.4.md#known-limitations) still apply, and:

- **A preview shows no cost before you start it.** Its passages and tokens appear on its page once it exists, because the estimate needs the candidate profile. Until you switch or discard it, the knowledge base holds two sets of passages and vectors, and nothing expires a forgotten preview.
- **The comparison measures retrieval, not answers**, and only for the knowledge base's own evaluation sets (an agent's sets are not run). With few or easy questions it cannot tell two indexes apart, and a difference of one or two questions is noise. A knowledge base without evaluation sets has nothing to compare; you can still switch or discard.
- **The comparison runs count against the team's query usage** like any evaluation run.
- **Chunker v2 is unmeasured** (above), and its merge floor (a quarter of the passage size) is a judgment, not a tuned value.
- **A discarded preview leaves one small hidden profile row**, because a profile with migration history is never deleted; it is in no list.
- **The preview's own page is not in the automated page walk** (it needs a held migration); it was checked by hand and by the cluster acceptance.
