# Grounded v0.10.0

**Private content, first part, and a hardening pass.** v0.10.0 lets a team restrict a source to groups and people, with
the restriction applied everywhere a document's text is shown or used in an answer. It also carries a pass over the
whole codebase: answers start sooner, the chat stays fast in long conversations, a bug that garbled web pages in some
character sets is fixed, and the code and its tests are easier to work on.

An install that changes nothing keeps working as v0.9.0 did, only faster. **Document permissions are off** until a
platform admin turns them on.

The connectors planned for this release (Microsoft 365, Google Drive and others) move to v0.11.0.

## What's new

- **Document permissions** (B6, #41; [guide](../document-permissions.md)). Team editors can restrict a source to
  groups (as your identity provider names them, from sign-in or SCIM) and people (verified email addresses) in the
  source's new **Access** tab.
  - Its documents, including ones added later, are then searched, used in answers and opened only for those people.
  - The reader's permissions are checked wherever a document's text would be shown or used: search, agent answers in
    every channel, citations and the source viewer, whole-document text and passages, repeated-block samples and
    evaluations.
  - Only a signed-in person, or their own connected app on MCP, reads a restricted document. API keys, public and
    widget visitors, shared links and evaluation runs read unrestricted documents only.
  - An agent whose knowledge has restricted documents doesn't use the answer cache, and a conversation that cites one
    can't be shared.
  - **Off by default.** A platform admin turns on **Document permissions** (Admin → Settings → Features) after the
    upgrade has rolled out everywhere, because a server of the previous release would ignore restrictions. It can't
    be turned off while anything is restricted.

## Faster

- **Answers start sooner.** Before the first model call, one question made dozens of database round trips, one after
  another. A follow-up question in the app now makes 51 instead of 64, a question on a public agent 52 instead of 95,
  and a knowledge base search 19 instead of 24. A test keeps these counts from growing.
- **Keyword and vector search run side by side** instead of one after the other.
- **Long conversations stay quick.** A new question reads the conversation's latest 200 questions and answers, not
  every message with its stored sources. In the chat, earlier answers are no longer drawn again for every word that
  streams in or every character you type, and an open citation card stays open while the answer continues.
- **Pages ask the server less often.** What a page has just loaded counts as fresh for 15 seconds, so opening a dialog
  or returning to a list doesn't fetch it again. Changes you make still show at once.
- **A lighter first load.** The app's entry script is 18% smaller (51.6 kB to 42.1 kB compressed).
- **Fewer reconnections to the model gateway.** Up to 32 idle connections are kept per gateway instead of 2, which
  matters for a gateway that speaks HTTP/1.1.
- **Crawling pages with many links is far cheaper.** A source's exclude patterns were compiled again for every link
  of every page; they are compiled once (28 times faster in the benchmark).
- **Deleting is cheaper.** Deleting documents, expired anonymous sessions and their conversations no longer scans
  whole tables (migration 00069).

## Fixed

- **Web pages in other character sets were garbled.** A page that declares an encoding other than UTF-8 or
  windows-1252 (Cyrillic windows-1251, Central European ISO-8859-2, Japanese Shift_JIS and others) was decoded as
  windows-1252 before its own character set was applied, so its text was indexed as nonsense. Pages are now read in
  the character set they declare. **Pages indexed before the upgrade are not re-read automatically**: they are
  corrected the next time they change, or when you fetch them again from the document's page. If you have such
  sources, re-fetch their pages after upgrading.

## For contributors

- The Go test suite runs in under a quarter of the time (759 s to 169 s on a 12-core machine; CI's `test` job went
  from about 38 minutes to about 20). Each integration test's database is copied from a template migrated once, and
  the API tests run in parallel.
- No Go file is over 500 lines and no function over 80, and `make lint` now fails above those (it was 600 and 100).
- `npm run build` in `web/` no longer type-checks; `npm run typecheck` and `make web-test` do.
- The pass's larger findings, which need design decisions, are issues #249 to #253.

## Database and upgrade

Schema **69**, up from 67. Both migrations are expand-only, and old and new code run together on schema 69; the
`upgrade` job checks that the v0.9.0 image still serves the migrated schema.

- **00068** (document permissions) adds columns, two tables and a trigger, and builds one index **concurrently**. It
  changes no existing row.
- **00069** adds six indexes and nothing else, each built **concurrently**, so writes go on while they build.

Both run outside a transaction. A concurrent build waits for transactions that were open when it started. **During
the upgrade, don't start pods from the previous release.** If a migration seems stuck, look for a long-open
transaction in `pg_stat_activity` and end it. If an earlier attempt was interrupted, the migration drops the leftover
invalid index and builds it again. On a large install the index builds take time in proportion to the `documents`,
`conversations`, `audit_log` and `contextual_calls` tables.

There are no new settings. Follow the [upgrade guide](../operations/upgrades.md), verify a backup, and pin **both** the
application and OCR images to the published digests. With Helm, use the chart version that matches the release. Turn
on document permissions only after every pod runs v0.10.0.

## Known limitations

- **Document permissions are set per source**, by hand. Per-document permissions arrive with the connectors in
  v0.11.0. A person's groups change at their next sign-in, or at once through SCIM.
- **Pages garbled by the character-set bug stay garbled until they change or are fetched again** (see "Fixed").
- **A page that declares its character set only in the HTTP `Content-Type` header**, with no `<meta charset>` and no
  byte-order mark, is still read as windows-1252 unless it is valid UTF-8.
- **The 15-second freshness** means a page can show data up to 15 seconds old when something changed it elsewhere (a
  colleague, a background job). Pages that follow running work (ingestion, evaluations, migrations) poll as before.
- The performance numbers above were measured on the test suite and a development machine with the fake model
  gateway, not on a production install under load. Capacity at the design's size is still issue #89.
