# Grounded v0.1.0

This is Grounded's first release, and the release that makes the repository public. Grounded is an open-source, multi-tenant RAG and agents platform. Teams turn files and websites into knowledge bases and publish agents that answer only from them, with citations. Platform admins govern models, data classification, moderation, retention and access. The full list of changes is in the [changelog](../../CHANGELOG.md).

Release candidates are tagged `v0.1.0-rc.N` before the final `v0.1.0`. These notes cover both.

## Highlights

- **Teams, sources, knowledge bases and agents.** Upload files or crawl websites, combine them into knowledge bases with hybrid retrieval, and publish versioned agents with strict grounding and numbered citations.
- **Three audiences and three channels.** An agent can serve its team, everyone who signs in, or the public, through the web UI, an embeddable widget, or the OpenAI-compatible API (`agent:{team}/{agent}` on `POST /v1/chat/completions`).
- **Governance built in.** Classification levels limit which models see which data and who may use an agent. Public agents are moderated and fail closed. Retention runs with a dry-run report, legal holds stop deletion, break-glass access is time-boxed and audited per read, and every change goes to the audit log.
- **Optional SystemOne models** check each cited claim against its source, re-rank passages, drop prompt injections and spot off-topic questions. Every one of these features is off until an admin turns it on.
- **Ready for Kubernetes.** A generic Kustomize base with components and example overlays, signed multi-arch images, zero-downtime upgrades with expand/contract migrations, `grounded doctor`, key rotation, maintenance mode, and embedding-profile migration.
- **Observable.** Prometheus metrics, five Grafana dashboards, 23 alerts with runbooks, and SLO burn-rate rules.
- **Tested end to end.** CI runs a Playwright suite with axe accessibility checks, an authorization matrix over every API route and kind of caller, a kind smoke test of the manifests, and an upgrade test.
- **Try it with Docker only.** `make demo` seeds a sample team over the Go documentation and answers with a built-in fake model, so no model keys are needed ([`demo.md`](../demo.md)).

## Requirements

| Dependency | Version and notes |
|---|---|
| Kubernetes | 1.30 or later, with a CNI that enforces NetworkPolicy. The manifests are validated against the 1.34 schemas. `kubectl` 1.27+ or `kustomize` v5. |
| PostgreSQL | **17**, with **pgvector 0.8 or later** (filtered vector search relies on its iterative index scans) and the `vector`, `citext`, `btree_gin` and `pg_trgm` extensions. Use the `postgres-single` component, CloudNativePG 1.26+ (`postgres-cnpg`), or a managed service. |
| Valkey or Redis | Valkey or Redis **7 or later**, as one endpoint. Grounded doesn't speak the Sentinel protocol, so for high availability use a managed service or a proxy that presents one endpoint. Valkey holds only state that can be rebuilt. |
| Object storage | An S3-compatible bucket for original files and parsed text. Keep backups on a different storage system. |
| Model gateway | Any **OpenAI-compatible** gateway (LiteLLM, vLLM, SGLang, a hosted API) serving at least one chat model and one embedding model. Retrieval as a tool needs tool calling. Public agents also need a moderation provider: a `/moderations` endpoint, a guardrail model, a chat model used as a classifier, or a SystemOne model. |
| Identity | An **OIDC provider** with a confidential client whose redirect URI is `<APP_URL>/auth/callback`. |
| Ingress | TLS termination, because `APP_URL` must be `https://`. The ingress must not buffer responses, since chat answers stream over SSE. |
| Optional | An SMTP relay for email notifications, Apache Tika for extra parsing, Prometheus and Grafana (or Mimir), and a SystemOne service. |

To build from source you need Go 1.26 or later and Node 22 or later.

## Installing

There is no previous release, so every install of v0.1.0 is a first install. The [Kubernetes guide](../deployments/kubernetes.md) has the details. In outline:

1. **Write an overlay** in your own repository. Reference the base and the components you need at the release tag, for example `https://github.com/ncecere/grounded//deploy/kubernetes/base?ref=v0.1.0`, or start from [`example-small`](../../deploy/kubernetes/overlays/example-small/kustomization.yaml) or [`example-ha`](../../deploy/kubernetes/overlays/example-ha/kustomization.yaml).
2. **Pin the image by digest.** The GitHub release lists the digest for `ghcr.io/ncecere/grounded:v0.1.0`. Verify it as shown [below](#verifying-the-images) before you use it.
3. **Create the secrets** `grounded-runtime` and `grounded-s3`, and `grounded-smtp` if you want email. Generate your own `ENCRYPTION_KEY` and `API_KEY_PEPPER` (`openssl rand -base64 32`) and back up `ENCRYPTION_KEY`, because losing it makes stored gateway keys unreadable. Grounded refuses to start with the example values from `.env.example`.
4. **Set the configuration**: `APP_URL`, the S3 endpoint and bucket, `OIDC_ALLOWED_EMAIL_DOMAINS`, `TRUSTED_PROXIES`, your instance identity (`INSTANCE_NAME`, `ORG_NAME`, `UI_LOGO_URL`, `SUPPORT_URL`), and `CRAWL_ALLOWLIST_SEED` if teams will crawl websites.
5. **Apply.** Migrations run in each pod's init container under an advisory lock. Then run `kubectl -n grounded exec deploy/grounded-api -c api -- /grounded doctor` to check every dependency.
6. **Make yourself platform admin.** Sign in once, set `BOOTSTRAP_ADMIN_SUBJECT` to your OIDC subject, and sign in again.
7. **Set up the platform** in the admin portal: a model connection, a chat model and an embedding profile; the classification levels' descriptions and model ceilings; and a moderation policy before you turn public agents on. Set retention periods only after your records management has confirmed them. Until you do, Grounded keeps everything except anonymous conversations ([`operations/retention.md`](../operations/retention.md)).
8. **Optionally, seed the demo** to see the install working: `kubectl -n grounded exec deploy/grounded-worker -c worker -- /grounded demo`.

Record your install's settings and policies in a [deployment profile](../deployments/README.md) that you keep outside this repository.

## Upgrading

There is no earlier release to upgrade from.

- **From a pre-release build** (a `sha-<commit>` image): take a backup, then pin the v0.1.0 digest as for any upgrade ([`operations/upgrades.md`](../operations/upgrades.md)). Migrations are forward-only.
- **If you vendored the base** with `make vendor-k8s` while the repository was private, switch to the remote base at `?ref=v0.1.0` and delete the vendored copy. Once the package is public, you can also drop the `private-registry` component.
- **Going forward:** each release's schema works with the previous release's code, so rolling upgrades need no downtime. Don't skip a release that its notes mark as required. From v0.2.0, CI's upgrade test checks every release against the one before it. Downgrades aren't supported: to go back, restore a backup taken before the upgrade.

## Known limitations

v0.1.0 is pre-1.0. Parts of the API, the configuration and the manifests may change in minor releases, and the release notes will say how to adapt. The project currently has one maintainer.

**Performance and capacity**
- **Model latency sets the pace, and one GPU is slow.** On a single-GPU host, a 27B chat model with thinking turned off took a median of about 14 s per answer (83 s with thinking on), and served about two streams at once. Turn thinking off for self-hosted Qwen3-style models with the chat model's `extraBody` ([`deployments/`](../deployments/README.md#self-hosted-models)). Measure your gateway's throughput before a large backfill, and set each connection's `requestsPerMinute` just below its limit.
- **SystemOne judging costs latency.** On one GPU, passage judging adds about 0.7 s per candidate. That's why it is off by default and judges 10 candidates when on ([`benchmarks/systemone.md`](../benchmarks/systemone.md)).
- **Capacity is measured on a laptop, not production hardware.** Load tests at twice the design estimates passed on a single-node kind cluster with the real manifests ([`benchmarks/load.md`](../benchmarks/load.md)): 100 streaming answers, retrieval, the OpenAI-compatible API, uploads and page reads together, every threshold met. Retrieval is bound by Postgres CPU (about 45 requests/s at 2 CPUs, 95/s at 4). A timed restore rehearsal (Postgres and the bucket destroyed, restored and verified) is written up in [`operations/restore.md`](../operations/restore.md). Load-test your own install with `make k8s-load`, and rehearse a restore, before relying on it.
- **Very large vector tables.** In one stress case (a 1.56M-row table in which each vector has many near-duplicates from other sources), HNSW recall dropped to 0.845. Partitioning the vector tables fixes this but isn't built yet ([`benchmarks/vector-gate.md`](../benchmarks/vector-gate.md)).
- **Availability.** The 99.9% target is a design target. It needs the HA topology (`example-ha`: CloudNativePG, three API replicas on separate nodes, and an HA Valkey service), which is validated as manifests but hasn't yet been proven by a long-running install.

**Optional pieces**
- **SystemOne is optional.** Without a SystemOne model, answers still carry citations to the passages they used, but claims aren't verified one by one, passages aren't re-ranked or screened for injection by a model, and there is no scope check. SystemOne needs a service that answers `POST /v1/systemone` ([`systemone.md`](../systemone.md), [ADR-0020](../adr/0020-systemone-models.md)).
- **Public agents need setup.** They need a moderation provider and the platform's public switch, which is why the demo's shared agent is for signed-in users only.

**Not in v0.1.0.** These are [roadmap](../roadmap.md) candidates, not commitments:
- cross-encoder reranking and in-product evaluation sets (A1b, A2);
- connectors (Microsoft 365, Google Drive, Confluence and others), document-level ACLs, crawling sites behind a login, JavaScript rendering, and OCR for scanned PDFs, which are skipped (B1–B6);
- PII scanning at ingest (B7);
- MCP support, Teams and Slack bots, client SDKs, webhooks, and configuration as code (C1, D1, D2, F3, D4);
- SSO group-to-team mapping, SCIM, in-app team requests, and cost reporting (E1, E4, E3, E2);
- OpenTelemetry tracing, partitioned vector tables, a Helm chart, and a translated UI (F1, F2, F5, E9).

**Smaller items**
- Only platform admins create teams. `TEAM_REQUEST_URL` can point people to your own request form.
- The default `CRAWL_USER_AGENT` points site owners to a `/bot` page that Grounded doesn't serve yet. Set a user agent with a real contact URL.
- The accepted findings in the [threat model](../security/threat-model.md#findings-and-accepted-risks) apply. For example, an auditor sending a malformed body to an admin write route gets `400` instead of `403`, and the distroless base image is referenced by tag.

## Verifying the images

Images are published to `ghcr.io/ncecere/grounded` for linux/amd64 and linux/arm64. The tags are `v0.1.0`, `v0.1` and `latest-release`; release candidates get only their own tag, such as `v0.1.0-rc.1`. There is no `latest` tag. Tags can move, so deploy by digest.

Each image is built only in CI (`.github/workflows/image.yml`), scanned with Trivy, and signed with cosign using keyless signing tied to the workflow's GitHub identity. Look up the digest for a tag, then verify it:

```sh
docker buildx imagetools inspect ghcr.io/ncecere/grounded:v0.1.0   # prints the index digest

cosign verify ghcr.io/ncecere/grounded@sha256:<digest> \
  --certificate-identity-regexp '^https://github.com/ncecere/grounded/\.github/workflows/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

For a stricter check, use `--certificate-identity https://github.com/ncecere/grounded/.github/workflows/image.yml@refs/tags/v0.1.0` in place of the regular expression. A successful verification prints the signature's claims, including the commit it was built from. `docker run --rm ghcr.io/ncecere/grounded@sha256:<digest> version` prints the version and commit.

## Checksums, SBOM and provenance

- **The image is the release artifact.** No separate binary archives are published, and the image digest serves as its checksum. The GitHub release lists the digest, and GitHub provides the tag's source archives.
- **SBOM and provenance.** Each image carries an SPDX SBOM and SLSA provenance (`mode=max`) as BuildKit attestations in its index on ghcr.io. The cosign signature covers the index, which lists them. They aren't separate release assets, so they always describe exactly the image you deploy. To extract them:

  ```sh
  IMAGE=ghcr.io/ncecere/grounded@sha256:<digest>
  docker buildx imagetools inspect "$IMAGE" --format '{{ json (index .SBOM "linux/amd64").SPDX }}' > sbom.spdx.json
  docker buildx imagetools inspect "$IMAGE" --format '{{ json (index .Provenance "linux/amd64").SLSA }}' > provenance.json
  ```

- **Dependencies and scans.** [`security/dependencies.md`](../security/dependencies.md) lists the direct Go and npm dependencies with their licenses, along with the latest `govulncheck`, `npm audit` and Trivy results.
