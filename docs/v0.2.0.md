# v0.2.0: measure answer quality, run many teams

Status: **v0.2.0-rc.1 released** (2026-09-29) and running on the reference install; v0.2.0 follows. Branch `release/v0.2.0` (started 2026-09-28). Scope comes from the roadmap review of 2026-09-28 ([`roadmap.md`](roadmap.md)); the owner's decisions are in §6.

**In v0.2:** A2 evaluation sets, E1 SSO group mapping, E2 cost tracking and budgets, B4 OCR, E15 command palette search, the small-fixes batch, and four operations items. **Later:** A13 citation marks per claim (a refinement of the existing citation checks). **Parked:** A1b reranking, until a rerank model is available to test with.

Every feature below is **optional**: off, or invisible to people who don't use it, until an admin or team turns it on.

---

## 1. Exit criteria

v0.2 is done when:
1. **Evaluations:** a team editor builds a set of questions for a KB (typed, imported or from a thumbs-down), runs it, and sees retrieval scores per question and over time. If time allows, a full-answer run scores the agent's answers too.
2. **SSO groups:** an IdP group mapped to a team role adds and removes members at sign-in, audited; hand-managed members are left alone.
3. **Costs:** with the mode on *Track only*, admins and team owners see spend per team, agent and model; with *Enforce*, a team over its budget is warned, then blocked.
4. **OCR:** with OCR on and a backend configured (Tesseract, Tika or a vision model), a scanned PDF becomes searchable; with it off, nothing changes.
5. **Search:** ⌘K finds teams, users, models, connections and conversations by name, for the people allowed to see them.
6. **Fixes and operations:** the small fixes (§4) and the operations items (§5) are merged; the reference install runs v0.2 from the remote Kustomize base.
7. **The version label:** the `v0.2.0` image reports exactly `grounded v0.2.0 (<commit>)` (v0.1.0 reported `v0.1`). The image workflow now checks this on every tag build and fails the release otherwise; `v0.2.0-rc.1` proves it before `v0.2.0`.
8. The usual gates: OpenAPI first, the authorization matrix classifies every new operation, tests and E2E with axe, lint limits, CI green, and a walkthrough by role before the release.

## 3. Features

### 3.1 A2: evaluation sets and regression runs

The agreed design, with the owner's decisions, is [`evaluations.md`](evaluations.md).

**What people see.** An **Evaluations** tab on a knowledge base and on an agent, for editors and above. Members and people chatting never see it; a platform setting turns the feature off entirely.
- **A set** is a named list of test questions. Each question says what a good result is: the document (or page) that should be retrieved, optionally a few phrases the answer must contain.
- **Adding questions:** type one in; import a CSV (`question, expected document or URL, must mention`); or, from a conversation, **"Add to evaluations"** on a thumbs-down answer or an answer with no sources, which prefills the question for the editor to complete. Only the question text is copied, never the rest of the conversation (ADR-0010).
- **Running:** a **Run** button with two kinds:
  - **Retrieval check** (default): no model calls, so it's free and fast. For each question it runs the KB's (or agent's) retrieval and reports whether the expected document came back, at what rank, and the set's recall@k and MRR.
  - **Full answer check** (if time allows in v0.2): asks the agent each question like a chat would, then scores whether the answer cited the expected document, whether it contains the must-mention phrases, and, if SystemOne citation checks are on, how many claims were supported. Tokens are counted as usage (and priced, with E2).
- **Results:** a table of questions (pass/fail, rank, what came back instead), the set's score, and a trend chart across runs. Two runs can be compared: which questions got better or worse.
- **Automatic runs (optional per set):** after a re-index, a profile migration switch or an agent publish; a drop in score notifies the team's editors.

**Backend.**
- Tables `eval_sets` (team, KB or agent, name), `eval_cases` (question, expected document ids or URL patterns, must-mention phrases), `eval_runs` (kind, trigger, status, config snapshot: agent version, profile, retrieval settings) and `eval_results` (per case: pass, rank, retrieved document ids, for full runs the answer id and scores).
- A River job per run; cases run with the team's query limits and a small concurrency. Retrieval checks call the existing `kbs.Retrieve`; full checks call the agent loop in a no-transcript mode (like the editor's Test panel).
- API: CRUD for sets and cases, CSV import, start run, list runs, run results, compare two runs. Audited: set and case changes, runs started.
- Retention: runs and results are kept per a new retention kind (default 180 days); legal holds don't apply (no user content beyond questions editors wrote).
- `ragbench`'s URL-judged sets become importable, so the lab benchmark and the product use one format.

### 3.2 E1: SSO group → team mapping

**What admins see.** Admin → **Access** (or Teams → a team → **Group mapping**): rules of the form *IdP group "registrar-staff" → team Registrar, role Editor*. A rule can target any team and role (owner, admin, editor, member).

**How it works.**
- At sign-in, Grounded reads a configurable claim (`OIDC_GROUPS_CLAIM`, default `groups`; Authentik sends it with the `profile` scope). For each rule the user matches, they're added to the team with that role, or their role is raised to it; for rules they no longer match, the membership **that the mapping created** is removed or lowered. Memberships added by hand are never touched (each membership records its source: `manual` or `sso:<rule id>`).
- The highest role wins when several rules match the same team.
- A dry run shows who a new rule would add or remove, from the last seen claims, before it's saved.
- Audited like any membership change, with the rule as the actor. Owners see "Managed by SSO group X" on such members and can't remove them by hand (they'd come back at the next sign-in).
- Optional: off until a rule exists. SCIM (E4) stays for later.

### 3.3 E2: cost tracking and budgets

The agreed design, with the owner's decisions, is [`costs.md`](costs.md).

**Modes**, a platform setting with per-team overrides: **Off** (default) · **Track only** · **Enforce**.
- **Prices:** per model, admin-entered, per unit the gateway reports: per 1M input tokens, per 1M output tokens, per 1M embedding tokens (or per 1M characters, for gateways that count characters), per request (moderation, SystemOne). Price changes are dated, so past spend isn't recomputed.
- **Track only:** spend from the usage ledger (it records chat, embedding, SystemOne and query usage already) priced by model. Admin → **Costs**: spend per team, agent and model over a date range, with a daily chart and CSV export. Team owners see their team's spend in Team settings → Usage. No limits, no warnings.
- **Enforce:** adds monthly budgets per team (and optionally per agent). At a threshold (default 80%) owners and admins are notified; at 100% the team's chats and ingestion are refused with a clear message, except that admins can raise the budget or grant a one-time extension. Public agents count against their team.
- Backend: `model_prices` (model, unit, price, effective from), `team_budgets`; a daily rollup table so reports don't scan the ledger; the enforce check runs next to the existing limits (the same place `chat_tokens_per_day` is checked).
- Currency is one platform setting (default USD); no conversion.

### 3.4 B4: OCR for scanned documents

The agreed design, with the owner's decisions, is [`ocr.md`](ocr.md).

**Optional and pluggable.** Admin → **Parsing** (new page, or a section of an existing one): OCR **off** (default) or on, with a backend:
- **Tesseract:** a small sidecar service (a new Kustomize component `components/ocr-tesseract`), HTTP in, text per page out. Languages are a setting.
- **Apache Tika:** the existing optional `components/tika`, using the `-full` image, which runs Tesseract inside Tika. Simplest if Tika is already deployed.
- **Vision model:** a model of a new kind `vision` in the catalog, called through the gateway page by page ("transcribe this page as Markdown"). Best quality on forms and tables; costs tokens (priced with E2), subject to the model's classification limit like any other model.

**Behaviour.** OCR runs only for pages with no text layer (the built-in PDF parser already detects them: today those documents fail with "may be scanned"). A document's record page says which pages were OCR'd and by which backend. Teams can turn OCR off per source (on by default once the platform has it). Page caps per document and per day keep costs bounded. Existing scanned documents that failed can be retried with one bulk action.

### 3.5 E15: the command palette finds objects

Today ⌘K finds pages, actions, and the agents, KBs and sources of the user's first ten teams. v0.2 adds:
- **Platform staff:** teams, users, models, connections, embedding profiles and shared sources, opening their admin pages or record pages.
- **Everyone:** their own conversations by title.
- A server search endpoint (`GET /v1/search?q=`) returns the matches the caller may see, ranked by name match, so it scales past ten teams and large user lists. The palette queries it as you type (debounced); the local lists remain for instant results.

## 6. Owner decisions (2026-09-28)

The owner said to start work with the recommendations; any of these can still change.

1. ~~**Evaluations default.**~~ On by default: editors see the tab, members never do, and a platform setting turns the feature off.
2. ~~**SSO mapping and hand-added members.**~~ Memberships added by hand are never changed by a rule, even when a rule would give a lower role.
3. ~~**Budgets at 100%.**~~ Chats and ingestion are both refused, with an admin extension.
4. ~~**OCR backend for the reference install.**~~ The Tesseract sidecar first; a vision model on the Spark later, for forms.
5. ~~**Costs currency and price entry.**~~ One currency (USD by default), prices per 1M tokens (or characters) and per request.
