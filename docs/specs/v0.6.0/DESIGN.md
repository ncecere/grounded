# v0.6.0 design notes: service desk building blocks

Status: **built and released in v0.6.0** (2026-10-16; [`releases/v0.6.0.md`](../../releases/v0.6.0.md)). The owner's working mode (2026-10-15): no separate spec gate; one item at a time, each verified on the cluster before the next. The scope and the main decisions are in [`../../v0.6.0.md`](../../v0.6.0.md); this file records what each item turned out to be, and the choices made while building it. Order: agent templates, team requests, conversation sharing, router agent, webhooks.

## 1. Agent templates (C4, [#27](https://github.com/ncecere/grounded/issues/27))

**As built.** A new agent can start from a template. Five ship with Grounded (service desk FAQ, policy explainer, course helper, public website assistant, internal knowledge assistant); a platform admin can save any agent they can edit as another, shared with every team.

- **Built-in templates are code, not rows** (`internal/agents/templates_builtin.go`): they follow the release, cannot be edited into something else, and a test pins their shape (valid configuration, no model, no knowledge bases, no tools, audience `team`). Saved templates are rows in `agent_templates` (migration `00049`, additive).
- **A template is how an agent answers, never what it answers from or who may use it.** `TemplateConfig` builds a template's configuration from the defaults and copies an allowlist of fields; the knowledge bases and their filters, the tools and the audience are never copied, so a template cannot make an agent public. `TestTemplateConfigClassifiesEveryField` fails when someone adds a field to the agent configuration without deciding whether a template carries it.
- **Using one.** `POST /v1/teams/{team}/agents` takes `templateId`. The template's appearance (accent, welcome message, starter questions) and configuration are the starting point and **every key of the request's `config` replaces the template's** (the person's knowledge bases and model). The template's description describes the template, so it is not copied to the agent. An unknown or deleted template is `404 template_not_found` and creates nothing. The audit entry of the agent names the template.
- **Who sees them.** `GET /v1/agent-templates` is for people who can make an agent (an editor, admin or owner of an active team) and for platform admins and auditors; not for plain members, anonymous callers or API keys. A saved template's instructions came from a team's agent, so they are not for everyone who signs in.
- **Decision (judgement, ADR-0011): saving needs ordinary access to the agent.** The owner decided that "a platform admin can save any agent as a platform-wide template". Platform admins have no default access to a team's content, agent configuration included (ADR-0011), and break-glass covers conversations and documents, not agent configuration. So saving requires a platform admin who is **also an editor, admin or owner of the agent's team**; an admin who is not gets the same 404 as for any team content, and one who is only a member gets 403. Nothing widens admin access. If the owner wants admins to template agents of teams they are not on, that needs a break-glass scope for agent configuration: an ADR amendment, not a flag.
- **Transparency.** Saving is audited in **the source team's** audit log (`agent_template.create`, with the agent's ID), so a team can see its agent was copied. Renaming and deleting are platform audit entries. The template keeps no link to the agent or the team, and deleting an agent or a template touches nothing else (an agent made from a template holds its own copy).
- **Names** are unique ignoring case and cannot equal a built-in's, so the picker never shows two that look alike.
- **UI.** New agent has **Start from** (a blank agent, or a template; a saved template's model is picked when the platform still offers it). Admin → **Agent templates** (Content group) lists them with View, Rename and Delete (saved ones, platform admins). **Save as template…** is in the agent's "…" menu for platform admins, with a warning that everyone who makes an agent can read the instructions.

**Not in this item:** team-level templates (the owner said they may come later), template versions, updating agents made from a template when it changes (an agent keeps its copy, by design).

**Docs to write at the release:** the Agents page of the docs site (Start from; Save as template), the Administration page for Agent templates, the release notes.

## 2. In-app team requests (E3, [#30](https://github.com/ncecere/grounded/issues/30))

**As built.** Anyone signed in can ask for a team (name, what it is for, the highest classification of its data, and optionally who should own it). Platform admins review the requests in **Admin → Teams → Requests**; approving creates the team in the same step, declining sends a reason. It is **optional and off by default**: a platform admin turns it on in Admin → Settings → Features. Off, the request page and its links disappear, new requests are refused (the API too, `403 team_requests_off`) and team creation stays with platform admins, as today. Requests already open stay in the queue until someone decides them.

- **Who may ask.** People signing in (not API keys). An optional **SSO group** limits it: the person's groups as last seen at sign-in (`sso_user_groups`, matched ignoring case) must include it, and someone whose sign-in carried no groups cannot pass (`403 not_allowed_to_request`). A **limit on open requests per person** (default 2, 1 to 20) refuses the next one (`409 too_many_open_requests`); it is checked under a lock on the settings row, so two requests made together cannot both get past it. The three gates are checked in the order a person should hear of them: the switch, who may ask, how many are open.
- **What a request holds.** Name (1 to 80), purpose (required, up to 1,000: reviewers need it), the classification, and an owner email (empty means the requester). It has **no address**: the reviewer chooses one when approving, with the name and classification pre-filled and changeable.
- **Approving is one transaction.** It locks the request, checks it is still pending and the revision matches (`If-Match`), creates the team (`teams.Service.CreateTx`, split out of `Create` for this), makes the optional **first agent** from a template (`agents.Service.CreateStarterTx`: a draft named after the template, team-only, never published), records the decision, audits and notifies. A failure anywhere (`409 slug_taken`, `404 template_not_found`, a bad classification) leaves the request pending and no team behind; a test with a mutant that creates the team in its own transaction pins this. The owner is the requester, or the person named: someone who has never signed in is invited by email through the normal invite flow, and the requester is told either way. The team's description is the request's purpose.
- **Declining** needs a reason (up to 500) that the person reads on their page and in the notification. A declined request is closed; the person asks again if they want to.
- **Notifications.** A new request reaches the platform admins (`team.request_new`, in their notification settings under platform admins); the decision reaches the requester (`team.request_decided`); the named owner hears through the team invitation or the "you were added" notice as for any team.
- **Audit.** `team_request.create`, `.withdraw`, `.approve` and `.decline`, and `platform.team_requests` for the switch and limits. Approve is also in **the new team's own audit log**, so the team can see how it came to be.
- **Who sees what.** Platform admins and auditors read the queue (the purpose is the requester's own text, not team content); only platform admins decide. A person sees only their own requests; asking about someone else's request id is the same 404 as for one that does not exist. Withdrawing works while the feature is off.
- **The old link.** `TEAM_REQUEST_URL` stays the fallback while the feature is off. When it is on, "Request a new team" in Home and the workspace switcher goes to the in-app page (the switcher offers it to everyone, not only people without a team).
- **UI.** `/team-requests` (the person's requests, New request, Withdraw); Admin → Teams gains a **Requests** tab with the number waiting (the sidebar shows it beside Teams, and the Overview lists it under what needs attention), with Approve…, Decline… and View…; Admin → Settings → Features has the **Team requests** switch and **Who may ask…**.

**Judgement calls.** Auditors can read the queue (as they read domain requests). A platform admin may ask like anyone else. A request cannot be edited (withdraw and ask again). The reviewer, not the requester, picks the address.

**Not in this item:** editing a request, a request for a change to an existing team, email to the requester beyond the ordinary notification channel, per-group limits.

**Docs to write at the release:** the Administration page for team requests and the Settings page's Features, the Using page for requesting a team, the release notes.

## 3. Conversation sharing (C12, [#29](https://github.com/ncecere/grounded/issues/29))

**As built.** A person can make a link to a **read-only view of their own conversation**: the questions, the answers and their citations, up to the last finished answer at that moment. Whoever the link is for opens it; the owner revokes it any time. It changes ADR-0010 (transcripts belong to the user), so the ADR is amended in this item: sharing is the user's own deliberate act, and nothing else about who can read a transcript changes.

- **A share is a pointer, not a copy.** `conversation_shares` names the conversation and `up_to_seq`, the last message it covers. Messages are never edited or removed one by one, so those messages *are* the snapshot, and no second copy of anyone's transcript exists to retain, hold or leak. `TestMessagesAreAppendOnly` fails if any code starts editing or deleting a message, because a share would then have to copy first. Deleting the conversation ends every share of it: the user's deletion at once (the view checks `deleted_at`), and retention's purge by the foreign key's cascade; a legal hold holds the conversation, and so its rows, as ever.
- **Who can open it, decided in one place (`openShare`).** *People who may chat with the agent* (`agent_users`, the default): the agent's audience as chatting decides it (`mayUse`: its team, everyone signed in, or, for a public agent, everyone signed in while public access is on). *Anyone with the link* (`anyone`): only for a **public** agent with public access on, and it is checked again every time it is opened, so turning public access off or narrowing the agent closes it to people outside the team without touching the link. A link is the owner's: it works only while its owner is an active person who may still chat with the agent, for everybody including them (v0.6.1: it used to open for the owner whatever had happened to them). If they leave the team, are suspended or lose access it stops, and it comes back with their standing, since nothing is deleted. A link is closed when its agent is disabled (by the team or the platform), unpublished or deleted, or its conversation is deleted.
- **No oracle.** Without a session, every refusal is the same `401 sign_in_required`, including a secret that does not exist, so valid and invalid links cannot be told apart by someone who does not hold one; the page then asks for a sign-in. With a session, every refusal is `404`. A secret is 32 random bytes (43 characters, one spelling) and only its SHA-256 is stored, so a database copy holds no link; the link is shown **once**, when it is made (a later list shows when, how many messages and who it was for, never the link).
- **What a viewer reads, and what they never do.** Questions, answers, their citations (title, headings, pages, the snippet the answer showed, the web address when the agent linked its sources). Never feedback, the model's reasoning, the agent's steps, the search it ran, SystemOne's checks, tokens or timings: the response type has no such fields (`SharedMessage`), and a test checks the JSON for every one. A tool's result is named and its text is not shown, since it is not the team's knowledge base. The sharer's name is shown only when they tick **Show my name**.
- **Sources open as they would after asking.** `GET /v1/shared/{token}/messages/{id}/sources/{n}` serves the passage through the same code the source viewer uses, only for an answer inside the snapshot and only a passage it cited (a later answer, or another conversation's, is `404`); the agent's claim checks are left out and the whole document is never offered. A viewer sees no more than they would by asking the agent the same question; that is the principle behind letting the agent's audience be the gate.
- **Making a link.** The conversation's owner, signed in: not an API key, even a personal one that can read the conversation (they get 401), and anyone else gets `404`. Needs a finished answer (`409 nothing_to_share`; a stopped answer does not count), an available agent (`409 agent_unavailable`), a public agent for `anyone` (`409 public_share_unavailable`), and at most 10 links per conversation (`409 too_many_shares`), checked under a lock on the conversation. A later message is not in an earlier link; make a new one to share more.
- **Not for teams.** Sharing is audited in the **platform** log only (`conversation_share.create` and `.revoke`: who, and whether it is open to anyone), with no team, agent, conversation or content, and never in a team's own audit log (teams never see who a user is; conversation deletion is not audited either). Reading a shared answer of a Sensitive or Restricted agent is written to the access log (channel `shared`) as using it is; the owner's own reading and opening a source are not another use.
- **Referrers and indexing.** The address holds the secret, so the app shell for `/shared/` and the API answer `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex` and (the API) `Cache-Control: no-store`; the page also asks for no referrer, and external source links already use `rel="noreferrer noopener"`.
- **UI.** **Share…** in a conversation's "…" menu (the chat page, Conversations): who can open it (an open link only for a public agent), Show my name, a warning that it can't be taken back, **Create link** and the link shown once with Copy, and the links made with Revoke. The shared page is `/shared/<secret>`, outside the app shell so it reads the same signed in or not: a notice that it is a read-only snapshot, the thread with its sources opening beside it, **Ask the agent**, and a sign-in prompt when the server asks for one.

**Judgement calls.** Links cannot be edited, only made and revoked; no expiry beyond the conversation's own retention (the owner revokes, as the design said); the sharer's name is the display name only (never the email); no per-link view counts (they would make a second record of who read what).

**Not in this item:** a share of part of a conversation, sharing to named people, comments, an expiry setting, or reading a share through the API with a key.

**Docs to write at the release:** the Using page for sharing, the retention and privacy pages (ADR-0010's amendment), the Administration page for the access log's new channel, the release notes.

## 4. Router agent (C5, [#28](https://github.com/ncecere/grounded/issues/28))

**What it is.** A **router** is an agent that answers nothing itself: each question goes to the best other agent the asker could open on their own, and the router shows that agent's answer, names it, and links to the conversation where the asker can carry on. When no agent fits, it says so, and the question lands in the router's gap report. Two settings make it: **Can be reached through routers** on an ordinary agent (off by default) and **Route questions to other agents** on the router.

- **Both are part of the agent's configuration** (`routable`, `router`), so they follow publishing, versions and the version history like every other setting; nothing new to migrate. A router cannot also be reached through routers (no loops), and a router has no knowledge bases (publishing asks for none, and refuses them: a router that also searched would have two ways of answering).
- **Candidates are the directory, filtered.** The agents the asker may chat with (`Service.Directory`: the same gate as everywhere, `mayUse`, including the public switch and an API key's reach), whose *published* version is `routable`, active, not routers, not the router itself. A public router therefore reaches only public agents (an anonymous asker could open nothing else), a signed-in router also reaches signed-in agents, and a team router reaches whatever its asker may use. No new access rule: **the router can never show someone an answer they could not have asked for.** At most 25 are considered (by name); more is a warning on the router's page, not a silent cut.
- **The choice is one SystemOne request** (`systemone.Route`, after the scope check: a choice among the candidates described by name, description and a summary of their instructions, plus *small talk* and *none*; it reuses the scope feature's model, thresholds' timeout and slots). Chosen below 0.5 confidence counts as none. Without the SystemOne scope check switched on, a router **cannot be published** (a problem on Publish, like moderation's) and, if it is switched off afterwards, answers as if nothing fit (the decision is recorded as `unavailable`).
- **Delegation is an ordinary chat with the target** (`Service.Chat` for a signed-in asker, `PublicChat` for an anonymous one), so the target's own limits, budget, moderation, citations and audit apply and are the target team's. It makes (or, when the previous routed turn went to the same agent, continues) a conversation with the target that belongs to the asker: that is the "continue there" link, `/a/<team>/<agent>?c=<id>`. The router's conversation keeps the question and a copy of the answer with its citations, so it reloads, exports and opens sources like any answer.
- **What the router's own turn records.** The routing decision in `message_events.routing` (decision `routed`, `none`, `small_talk` or `unavailable`, the confidence, the number of candidates, the latency; the chosen agent's ID, never the question) and, on the message, `routedTo` (agent, team, conversation, message) for the "Answered by …" line. A question that fits nothing is stored as a gap with the new signal `no_agent`, grouped under the platform's default embedding profile (a router has no knowledge bases to take one from).
- **Small talk** ("hi", "thanks") is answered by the router's own model, briefly, like any agent's.
- **Not shareable.** A router conversation holds answers from agents whose audience is not the router's, so **Share…** refuses it (409 `not_shareable`); exporting your own conversation is unchanged.
- **Feedback** on a routed answer is the router's (its team sees it), not the target's.
- **UI.** *Settings → Reach*: "Can be reached through routers". The New agent dialog's templates gain **Front door (router)**; a router's editor replaces Knowledge bases with **Routing** (what it can reach right now, from the editor's own access, and the wording when nothing fits, which is the refusal message). The chat shows "Answered by *Agent* · *Team*" with a **Continue there** link under a routed answer.
- **Audit.** Nothing new beyond the version history: the settings are configuration. The routed question is an ordinary answer in the target's analytics.

**Judgement calls.** One level: a routed agent answers; it is never asked to route again. The router decides from names, descriptions and summaries, not from a search of the targets' content (cheap, private, and what the owner asked for). No per-agent weighting, no allow-list of targets yet (the flag is the allow-list; a router can be narrowed later).

**Not in this item:** a list of targets chosen on the router, routing to several agents at once, handing over to a person (C3), sharing a router conversation.

**Docs to write at the release:** the Using page for routers and the Agents page for the two settings, the SystemOne page (the routing question), the release notes.

## 5. Webhooks (F3, [#26](https://github.com/ncecere/grounded/issues/26))

**What it is.** Another system hears about things that happen in Grounded: Grounded sends it an HTTPS `POST` with a small JSON event, **signed** so the receiver can tell it came from Grounded, and **retried** when the receiver is down. Recorded decisions ([`docs/v0.6.0.md`](../../v0.6.0.md)): platform admins turn webhooks on and approve destinations; team admins and owners create webhooks for their own team's events, to approved destinations only; platform admins also get platform-wide events; every webhook and every change is audited; events carry **IDs and summaries, never transcripts or document text** (a receiver that needs more fetches it through the API with a key, so classification and permissions still apply).

- **The switch and the destinations.** *Webhooks* in Admin → Settings → Features, **off by default** (as team requests). Off means no new webhooks, no events recorded and nothing sent; what exists is kept. **Approved destinations** are host patterns a platform admin lists (`hooks.example.edu` or `*.example.edu`, normalised like the crawl allowlist; `*` alone is refused). A webhook's URL must be `https` on the default port and its host must match a pattern, **when it is saved and again before every delivery**: removing a destination stops what is sent there at once (the delivery fails as "no longer approved" and is not retried).
- **The address guard** is the crawler's: a delivery resolves the host, refuses every private, loopback, link-local, CGNAT, multicast and cloud-metadata address (the crawler's `PublicAddr`), connects to the address it checked (no rebinding), follows **no redirects** (a `3xx` is a failure) and reads at most 4 KB of the answer. Loopback is only reachable by tests.
- **Who sees what.** A **team webhook** is managed by the team's admins and owners (Team settings → Webhooks); editors and members do not see them, and a platform admin who is not on the team gets the same `404` as for any team content (ADR-0011). A **platform webhook** (no team) is managed by platform admins in Admin → Webhooks; auditors read. A webhook receives only its own scope's events: a team webhook the team's events, a platform webhook the platform's, so **no webhook sees another team's events**. Up to 10 webhooks per team and 10 platform-wide.
- **Events** (`GET /v1/webhook-events` lists them; a webhook subscribes to at least one): team events `source.synced` (a web source finished syncing: counts of pages added, changed, removed), `source.sync_failed` (a sync failed: a short error), `agent.published` (agent, version, audience), `feedback.submitted` (agent, message ID, rating and reason: **never the question, the answer, a comment, or who**); platform events `team.created` and `team_request.created`; and `webhook.test`, sent on request. Each is `{id, type, createdAt, team?, data}`; `id` is stable across retries and redeliveries (receivers de-duplicate on it).
- **Signing.** Every webhook has a secret (`whsec_…`, 32 random bytes) **shown once**, when the webhook is made and when it is rotated; Grounded keeps it **encrypted** (the key-rotation machinery re-encrypts it) because it must sign with it. A delivery carries `Grounded-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256(secret, "<t>.<body>")>`, `Grounded-Event`, `Grounded-Delivery` (the delivery's ID) and `Grounded-Webhook`. A receiver checks the signature over the raw body and that `t` is recent (five minutes); the docs show it in a few lines.
- **Delivery and retries.** Recording the event and queueing its deliveries happen **in the transaction that made the change** (an outbox: a rolled-back change sends nothing). A delivery is a River job with a 10 s timeout and **8 attempts** (15 s, 1 min, 5 min, 30 min, 2 h, 6 h, 12 h: about a day). Any `2xx` is delivered; anything else is a failure and is retried, except `410 Gone`, which ends it and **pauses** the webhook. After **5 deliveries in a row** gave up, the webhook is **paused** (`failing`), and the team's admins and owners (platform admins for a platform webhook) are notified (`webhook.paused`); one success resets the count, and turning it back on is a deliberate edit.
- **The delivery log.** Each webhook keeps its deliveries (event type, status, attempts, the last answer's status and a short error, never the receiver's body) for **14 days**, with **Send test event** and **Redeliver** (same event ID, a new delivery). The payload is IDs and summaries, kept with the delivery so a redelivery is the same event.
- **Audit.** `webhook.create`, `.update` (what changed, never the secret), `.rotate_secret`, `.delete`, `.test`, `.redeliver`, `webhook_destination.create` and `.delete`, `platform.webhooks` for the switch; team webhooks in the team's audit log, the rest in the platform's.
- **API** (OpenAPI): `GET`/`POST /v1/teams/{team}/webhooks` and `GET`/`PATCH`/`DELETE …/{id}` (`If-Match`), `POST …/{id}/rotate-secret`, `POST …/{id}/test`, `GET …/{id}/deliveries`, `POST …/{id}/deliveries/{deliveryId}/redeliver`; the same under `/v1/admin/webhooks`; `GET`/`PUT /v1/admin/settings/webhooks`; `GET`/`POST /v1/admin/webhook-destinations`, `DELETE …/{id}`; `GET /v1/webhook-destinations` (the patterns, for team admins choosing a URL); `GET /v1/webhook-events`; `webhooks` in the `me` capabilities. One additive migration (`00053_webhooks.sql`).

**Judgement calls.** Platform webhooks do not receive teams' events (least privilege; platform admins see teams' metadata in the audit log, not a firehose of their activity). `https` on port 443 only, as the crawler's 80/443. No custom headers or bodies, no per-event filters beyond the event types, no batching. Secret rotation takes effect at once (no overlap window); a receiver that needs one accepts two secrets during the change. Deliveries are at least once and not ordered: receivers use the event ID and `createdAt`.

**Not in this item:** webhooks for every audit event, per-agent or per-source filters, a receiver-side SDK, delivery to non-HTTPS or non-443 destinations, signing with asymmetric keys.

**Docs to write at the release:** the Administration page for webhooks (switch, destinations), the Team page for creating one, a Webhooks reference (events, payloads, signature check in a few languages, retries), the release notes.
