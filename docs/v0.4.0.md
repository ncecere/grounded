## 1. Answer cache (A8)

A question that was answered recently, under the same conditions, gets the stored answer again instead of the whole pipeline (rewrite, search, SystemOne judging, the model, citation checks, buffered moderation): well under a second, at no model cost, with the same citations and claim verdicts as the original.

### When an answer is reused

All of these must hold:

- **The same published agent version.** Publishing a version (model, instructions, knowledge bases, settings) starts a fresh cache.
- **The same knowledge.** Each knowledge base gets a `content_revision`, raised whenever a document is added, changed, re-crawled or deleted, or the knowledge base moves to another embedding profile. The cache key includes the revision of every knowledge base the agent uses.
- **The same answering settings:** a settings revision covers the platform's and the agent's moderation and SystemOne settings.
- **The same question.** By default the match is **exact** after normalising (case, whitespace, trailing punctuation). Optionally (decision 1), a **near-identical** question matches too: the nearest cached question by embedding, above a high similarity, confirmed by SystemOne as asking the same thing, so "hours on Saturday" never gets "hours on Sunday".
- **A question that stands on its own:** the first message of a conversation, or a follow-up that doesn't lean on the conversation (`needsContext`, as for the query rewrite).
- **A clean answer:** passed moderation, no error, not refused because of a failure, and no thumbs-down since.
- **No MCP tool results:** tools return live data, so an answer that used one is never cached.
- **Not expired:** a per-agent time limit (decision 3).

Evaluations and Try it never read or write the cache.

### What a cached answer still goes through

The chat's limits (rate limits, query limits, budgets, concurrent chats), the conversation and message records (the message is marked `cached`), the audit and usage records (zero model tokens, channel as usual), and the same streamed events as a live answer (so the web chat, the widget, the public page, the OpenAI-compatible API and MCP need no changes). A thumbs-down on a cached answer removes the entry, so the next person gets a fresh one.

### Storage and lifetime

An `answer_cache` table in Postgres (shared by every pod, kept across restarts, a lookup by key in about a millisecond): agent version, normalised question and its hash, the knowledge-base revisions and settings revision of the key, the answer (text, citations, claims, sources), created, expires, hits, last hit. Cached answers follow the agent's retention rules and data classification like messages; a periodic job deletes expired entries. Editors can **clear an agent's cache** (Agent → Settings), and a platform admin can turn the cache off for the whole platform.

### Owner decisions (2026-09-30)

1. ~~Matching?~~ **Exact by default, with an option to also match near-identical questions confirmed by SystemOne** (per agent; needs a SystemOne model).
2. ~~Default?~~ **On by default for public agents; every agent has its own on/off setting** (Agent → Settings), whatever its audience.
3. ~~Expiry?~~ **24 hours by default**, configurable per agent.
4. ~~Visible to people?~~ **Invisible**: no "saved answer" note and no "ask again" in the chat. A stale answer goes away with the time limit, a thumbs-down, a change to the agent or its knowledge, or an editor clearing the cache. The audit and usage records and the agent's analytics (a cache-hit rate and the tokens saved) still show it.

### How it gets built

1. A migration: the `answer_cache` table, `content_revision` on knowledge bases (raised by ingestion, deletion and profile switches), a settings revision.
2. The cache service: normalising, eligibility, lookup and store, near-identical matching with the SystemOne check, eviction, the expiry job.
3. The chat pipeline: look up right after the limits are admitted; on a hit, replay the stored answer's events; on a miss, answer as today and store the answer if it qualifies.
4. API (OpenAPI first) and UI: the agent's cache settings (on/off, near-identical, time limit) and **Clear cache**, the platform switch, `cached` on messages, a cache-hit tile in agent analytics. Everything in the authorization matrix.
5. Tests for hits, misses and every invalidation above; metrics (hit rate, tokens saved); docs.
