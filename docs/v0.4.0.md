# v0.4.0: answers people trust and teams can improve

Status: **being designed** (owner, 2026-09-30). The scope and its order are in [`roadmap.md`](roadmap.md) § K: the unanswered-questions and gap report (C2, A15), cross-encoder reranking (A1b), an answer cache (A8), public answers streamed while they're moderated, and a document viewer with highlights with citation marks per claim (B10, A13). ## 1. Answer cache (A8)

A question that was answered recently, under the same conditions, gets the stored answer again instead of the whole pipeline (rewrite, search, SystemOne judging, the model, citation checks, buffered moderation): well under a second, at no model cost, with the same citations and claim verdicts as the original.

### When an answer is reused

All of these must hold:

- **The same published agent version.** Publishing a version (model, instructions, knowledge bases, settings) starts a fresh cache.
- **The same knowledge.** Each knowledge base gets a `content_revision`, raised whenever a document is added, changed, re-crawled or deleted, or the knowledge base moves to another embedding profile. The cache key includes the revision of every knowledge base the agent uses.
- **The same answering settings:** a settings revision covers the platform's and the agent's moderation and SystemOne settings.
- **The same question.** By default the match is **exact** after normalising (case, whitespace, trailing punctuation). Optionally (decision 1), a **near-identical** question matches too: the nearest cached question by embedding, above a high similarity, confirmed by SystemOne as asking the same thing, so "hours on Saturday" never gets "hours on Sunday".
- **A question that stands on its own:** the first message of a conversation, or a follow-up that doesn't lean on the conversation (`needsContext`, as for the query rewrite).
- **A clean answer:** passed moderation, no error, not refused because of a failure, and no thumbs-down since.
- **No MCP tool results:** tools return live data, so an answer that used one is never cached.
- **Not expired:** a per-agent time limit (decision 3).

Evaluations and Try it never read or write the cache.

### What a cached answer still goes through

The chat's limits (rate limits, query limits, budgets, concurrent chats), the conversation and message records (the message is marked `cached`), the audit and usage records (zero model tokens, channel as usual), and the same streamed events as a live answer (so the web chat, the widget, the public page, the OpenAI-compatible API and MCP need no changes). A thumbs-down on a cached answer removes the entry, so the next person gets a fresh one.

### Storage and lifetime

An `answer_cache` table in Postgres (shared by every pod, kept across restarts, a lookup by key in about a millisecond): agent version, normalised question and its hash, the knowledge-base revisions and settings revision of the key, the answer (text, citations, claims, sources), created, expires, hits, last hit. Cached answers follow the agent's retention rules and data classification like messages; a periodic job deletes expired entries. Editors can **clear an agent's cache** (Agent → Settings), and a platform admin can turn the cache off for the whole platform.

### Owner decisions (2026-09-30)

1. ~~Matching?~~ **Exact by default, with an option to also match near-identical questions confirmed by SystemOne** (per agent; needs a SystemOne model).
2. ~~Default?~~ **On by default for public agents; every agent has its own on/off setting** (Agent → Settings), whatever its audience.
3. ~~Expiry?~~ **24 hours by default**, configurable per agent.
4. ~~Visible to people?~~ **Invisible**: no "saved answer" note and no "ask again" in the chat. A stale answer goes away with the time limit, a thumbs-down, a change to the agent or its knowledge, or an editor clearing the cache. The audit and usage records and the agent's analytics (a cache-hit rate and the tokens saved) still show it.

### How it gets built

1. A migration: the `answer_cache` table, `content_revision` on knowledge bases (raised by ingestion, deletion and profile switches), a settings revision.
2. The cache service: normalising, eligibility, lookup and store, near-identical matching with the SystemOne check, eviction, the expiry job.
3. The chat pipeline: look up right after the limits are admitted; on a hit, replay the stored answer's events; on a miss, answer as today and store the answer if it qualifies.
4. API (OpenAPI first) and UI: the agent's cache settings (on/off, near-identical, time limit) and **Clear cache**, the platform switch, `cached` on messages, a cache-hit tile in agent analytics. Everything in the authorization matrix.
5. Tests for hits, misses and every invalidation above; metrics (hit rate, tokens saved); docs.

### As built (M4, [`answer-cache.md`](answer-cache.md))

Migration `00042_answer_cache`; `internal/answercache` (entries, the platform switch, agents' settings), `internal/agents/cache.go` (lookup, replay, store) and `cachesettings.go`; Agent → Settings → **Saved answers**, Admin → Overview → Features → **Saved answers**, the Usage tiles in agent analytics. In the UI the cache is called "saved answers". Where the design was silent:

- **Content revisions by triggers.** `knowledge_bases.content_revision` is raised by database triggers rather than in each code path, so every writer (ingestion, uploads, re-crawls, retries, deletions, retags, maintenance, profile migrations, the previous release during a rolling upgrade) is covered: a document finishing processing or changing its title, URL, tags or chunk counts, or deleted, raises every knowledge base its source is attached to through a **deferred** trigger at commit, once per source and transaction (bulk changes cost one update, and the knowledge base's row is locked only while the transaction commits, so concurrent ingestion doesn't queue on it); attaching or detaching a source and a source's or knowledge base's profile switch raise it at once. A boilerplate re-chunk, which changes passages without touching the document row's tracked columns, calls `raise_kb_content_revision` itself.
- **The settings revision** isn't a new column: the key hashes the existing revisions of the audience's moderation policy, `systemone_settings` and `rerank_settings` (read with the knowledge bases' revisions in one query); the agent's own settings are in its version. The audience is in the key too.
- **Per-person context.** No prompt carries the person (the system prompt names the agent, team, organisation and today's date). Retrieval is the agent's. MCP tools could act for the person, so an answer that called one is never saved. The **date** is in the key only for questions with relative-time words (today, tomorrow, this week, open, hours, deadline, weekday names…), so most answers live their full time limit.
- **Failed answers aren't cached** (the simplest choice for the gap report): refusals, "nothing found", out-of-scope and small-talk replies, answers with unsupported, contradicted or uncited claims (any gap signal), errors and moderation notices are answered live every time, so failures keep reaching the gap report.
- **What's eligible:** published versions in always mode with knowledge bases, a standalone question (`needsContext`, as the rewrite), every channel including stateless ones (the OpenAI-compatible API, service keys, MCP `ask`). Tool-mode agents aren't cached: their model chooses its searches, and replaying tool steps faithfully isn't worth it. Try it and evaluation runs never read or write it.
- **Where it sits:** the lookup runs right after the limits are admitted and the knowledge bases are resolved; on a hit, reranking and SystemOne plans are skipped, the question is stored, the conversation event sent, and the stored answer replayed (`retrieval`, `message_start`, one `text_delta`, `message_end` with citations, claims and uncited sentences: the buffered shape, so clients need nothing new). No status steps are sent. The store runs at the end of `finish`, after the answer was sent. Input moderation isn't run again for an exact hit (the same normalised text passed under the same policy revision); a near-identical hit runs it first (its words differ), and a block falls back to the live pipeline, which reuses that decision.
- **Near-identical:** the question is embedded once in the agent's embedding profile (the lowest profile ID among its knowledge bases, as for the gap report) and the vector goes into the request's embedding cache, so a miss's search doesn't embed it again (measured: one embedding per question either way). The nearest live entry with the same conditions at cosine similarity ≥ 0.92 is checked with a new SystemOne question (`same_question`, feature `cache`, threshold 0.8, 3 s time limit; a failure is a miss), using the platform's SystemOne model whatever the features' settings. Entries keep the vector even when near-identical matching is off, so turning it on works at once.
- **Storage:** one row per agent, conditions hash and question hash (a newer answer replaces it); entries of earlier versions or revisions stay unreachable until they expire. `message_events` gains `cached`, `cache_entry_id` (a thumbs-down on a reused answer removes the entry it came from) and `tokens_saved` (the original's input and output tokens, including the rewrite). The `cached` flag isn't in the conversation API: the cache is invisible to people.
- **Lifetime and retention:** an entry expires after the agent's time limit (1 hour to 30 days), capped at the transcript retention of the version's classification level (anonymous retention for public agents, signed-in conversation retention otherwise); a shortened time limit applies to existing entries at once. The retention run (every 10 minutes) is the periodic job: kind `answer_cache` (not configurable), deleting expired entries and those past that retention; legal holds on the team or agent keep them, never served.
- **Settings:** `agent_answer_cache` (no row: the defaults), not versioned and with its own If-Match revision; `enabled: null` follows the default (on for public). Clearing works whatever the switches. The platform switch is a one-row table read with a 5-second cache per process, like the MCP switch.
- **Deferred:** caching tool-mode answers; a per-team view of saved answers; a setting for the near-identical threshold.

## 2. Unanswered-questions and gap report (C2, A15)

Teams see what their agents fail at, grouped into topics, so they know what to add: "14 questions about parking permits got no answer this month" → add the parking page to the knowledge base.

### What counts as a failed question

Already recorded per answer (`message_events`, without content): **no context** (the search found nothing), a **strict refusal**, every passage **judged out** by SystemOne, **out of scope** (the scope check), a **thumbs-down** with its reason (`missing_sources`, `outdated`, `incorrect`, `wrong_sources`…), and unsupported or uncited claims. A question answered well later (for example after a source was added) closes its topic.

### The privacy question

ADR-0010: transcripts belong to the user; teams see aggregates and metadata only, never content or who asked. A report of *topics* needs the question text (or at least its meaning), so this changes ADR-0010 in some way. Options:

- **A. Counts only** (no change): failures by signal, agent, day and cited documents. No topics, so it can't say *what* to add.
- **B. Topics with a minimum crowd** (a small change): failed questions are kept apart from transcripts, embedded and grouped into topics; a model writes each topic's short label ("Parking permits"); teams see the label, the count, the signals and the trend, **never a question's text or who asked**, and a topic shows only once at least 3 different people asked about it (so a label can't point at one person). The stored questions follow the transcript retention and are deleted with their conversation.
- **C. B, plus shared questions** (A15): on a thumbs-down, the person may tick "share this question with the team" (off by default); shared questions show in full under their topic, can be added to an evaluation set in one click, and also count towards topics.
- **D. Show failed questions in full** to editors, with a notice to users: the most useful, the biggest change to ADR-0010.

### Still to decide (after the privacy model)

Who sees the report (editors, admins, owners; platform admins across teams?), how topics are formed and labelled (embedding clusters + a chat or SystemOne label), how often they're rebuilt, the actions on a topic (dismiss, mark fixed, add a source request, add to an evaluation set), notifications (a weekly digest?), and public agents' anonymous visitors.

### Owner decisions (2026-09-30)

1. ~~Privacy model?~~ **C: topics with a minimum crowd, plus questions shared on a thumbs-down.** Failed questions are kept apart from transcripts and grouped into labelled topics; teams see a topic's label, count, signals and trend, never a question's text or who asked, and only once at least 3 different people asked. On a thumbs-down, the person may tick "Share this question with the team" (off by default): a shared question shows in full under its topic and can be added to an evaluation set. ADR-0010 is amended accordingly.
2. ~~Who sees it?~~ **A team's editors, admins and owners** (on the team, alongside Evaluations and Agent → Analytics). Members don't; platform admins and auditors see counts only (failed questions per team and signal), never topics or shared questions.
3. ~~Topics and labels?~~ **Embedding clusters, labelled by the chat model.** Each failed question is embedded with the agent's embedding profile; a worker job regroups them hourly; once a topic has at least 3 different askers, the team's chat model writes its 2–5 word label from the topic's questions. The label is the only text shown for a topic without shared questions.
4. ~~Actions on a topic?~~ **Act on it, then let it close itself:** Add a source (Data sources, with the topic as a note), Add to evaluations (its shared questions), Dismiss (optional reason) and Mark fixed. A dismissed or fixed topic reopens on new failures; a topic closes itself when its questions start being answered well. Audited. No digest for now.
5. ~~Public agents' anonymous visitors?~~ **Included, each anonymous session counting as one person.** Their failed questions are kept as long as other failed questions (the agent classification's transcript retention), never linked to a visitor; the public page's footer adds that questions that can't be answered may be grouped, without the visitor's details, to improve the agent.

### How it gets built

1. **ADR-0010 amendment** (done with this design): failed questions and shared questions.
2. **Migration:** `gap_questions` (team, agent, the question's text and embedding, the signals, a pseudonymous asker key, shared or not, created; deleted with its conversation and by retention), `gap_topics` (team, agent, label, state open/dismissed/fixed, counts, first and last seen, reasons), and the link between them; a `shared` flag on feedback.
3. **Capture:** when an answer fails (the signals above) or gets a thumbs-down, the chat pipeline records its question (already embedded for the search, so no extra model call); a shared question is marked on a thumbs-down.
4. **Topics job** (worker, hourly): clusters each agent's open questions by similarity, keeps topics stable between runs, labels those reaching 3 askers with the chat model (metered as the team's spend), closes topics whose questions are now answered well, reopens on new failures, and prunes by retention.
5. **API** (OpenAPI first, authorization matrix): topics per team and agent with counts and trend, a topic's shared questions, the four actions, the share tick on feedback; counts per team for platform admins and auditors.
6. **UI:** a **Gaps** view (team, beside Evaluations; and per agent in Analytics), topic rows with signals and trend, a topic page with shared questions and the actions, the share tick in the thumbs-down form, the public footer line.
7. Tests (the 3-asker minimum, deletion with conversations, retention, reopening, permissions), metrics, docs.

### As built (M2, [`gaps.md`](gaps.md))

Migration `00041_gap_report` (`gap_topics`, `gap_questions`, `message_events.feedback_shared`); `internal/gaps` (service, topics job `gaps.topics`, labels, platform counts); the capture in `internal/agents/gaps.go` (called from `record`) and the feedback handler; the Gaps page, a topic's record page, Agent → Analytics → Gaps, Admin → Analytics → Failed questions, the share tick and the public footer line. Where the design was silent:

- **What's captured:** answers in stored conversations only (the web chat, the public page, the widget, personal API keys' conversations), since a question goes with its conversation; Try it, evaluation runs and stateless callers (service keys, the OpenAI-compatible endpoint, MCP) keep nothing. Errors, moderation notices and small talk aren't failures. Out of scope counts for non-strict agents too. Without an API-key pepper there's no asker key, so nothing is kept.
- **The vector:** the agent's embedding profile is the lowest profile ID among its knowledge bases (the same rule in the pipeline and the job); the vector the first search computed for that profile is reused (for a follow-up, the rewritten standalone question). A question without one (a thumbs-down, tool mode) is embedded by the job, metered to the team (usage source `gaps`). An agent without knowledge bases keeps questions but can't group them.
- **Grouping:** each new question joins the agent's topic with the nearest centroid at cosine similarity ≥ 0.8 (pgvector `<=>`), else starts one; the centroid is the mean of the topic's questions. Topics are never merged, so IDs stay stable.
- **The minimum crowd is strict:** a topic below 3 askers is hidden even when one of its questions was shared; it shows once it reaches 3. Counts are read live and leave out conversations their users deleted.
- **Closing by itself:** a good answer (citations, no failure signal) whose search vector is within 0.8 of an open topic counts towards it (nothing of the question is kept); after 2 such answers since the topic's last failure the job sets it `resolved` ("Answered now"). Dismissed, fixed and resolved topics reopen when a failure newer than their closing joins them.
- **Labels:** written once a topic reaches 3 askers and again when it has doubled; skipped while the team's budget is used up; the reply is cleaned to at most 5 words and 80 characters.
- **Feedback:** a thumbs-up after a thumbs-down removes the thumbs-down signal and the question if nothing else failed; the tick is in the thumbs-down menu, ticked before choosing a reason.
- **Retention:** no new retention kind: questions cascade with their conversations, so the conversation rules, grace period and legal holds apply unchanged; the job prunes topics with no questions left.
- **Actions:** Add a source is audited, then opens Data sources with the topic as a note and a new source's description prefilled. Add to evaluations works per shared question, into one of the agent's existing sets, with expected documents (evaluations require them). Audit entries carry IDs and states, never the label, since team audit logs are readable by platform staff.
- **Platform counts:** `GET /v1/admin/analytics/gaps` (default: the last 30 days), shown as a card at the end of Admin → Analytics → Top agents & teams. Members, keys and platform staff get 404 on team routes (session only, like evaluations).
- **Public footer:** the line is in the shared public chat, so the widget shows it too.

## 3. Cross-encoder reranking (A1b)

A reranking model (a cross-encoder, called through the gateway's `/rerank` endpoint as LiteLLM, vLLM and SGLang serve it; for example bge-reranker or Qwen3-Reranker) reads the question with each candidate passage and scores how well the passage answers it: more precise than the vector and keyword fusion, in one batched call. The `rerank` model kind already exists in the catalog; nothing uses it yet.

### Owner decisions (2026-09-30)

1. ~~With SystemOne judging?~~ **Rerank first, then judge only the best few.** The search fetches about 40 candidates; the reranker scores them in one call; SystemOne judges only the top few (instead of 10–20); without SystemOne, the top-ranked passages go to the model.
2. ~~Where is it set?~~ **A platform rerank model, on by default, with each agent able to turn it off.** Admin → Models chooses the rerank model (like the SystemOne model); once chosen, every agent, the knowledge-base Try it, the REST retrieval API and MCP `search` rerank. An agent can turn it off and set how many top passages to keep (Build → Advanced, default 6). Without a rerank model, retrieval is as today.

### How it gets built

1. The gateway client's `/rerank` call (Cohere/Jina request shape, as LiteLLM, vLLM and SGLang accept it), compatibility flags for servers that differ, a connection Test and stored health for rerank models.
2. The platform setting (the rerank model, like the SystemOne model) and the agent's `rerank` and `rerankTopN` config fields (OpenAPI first; a migration only if settings need a column).
3. Retrieval: fetch about 40 candidates, rerank them in one call, keep the top N for judging or the model; **fail open** (a rerank error or timeout keeps today's fusion order, with a time limit like passage judging's); the score shown in Try it and the retrieval API.
4. Metering (`rerank` requests and tokens, priced like other units), tracing spans, metrics, evaluations comparing runs with and without reranking.
5. Tests with a fake `/rerank` endpoint in the fake gateway; docs (operators: deploying a reranker; editors: the agent setting).

On the reference install, a rerank model has to be deployed on the gateway first.

### As built (M1)

Runbook: [`operations/rerank.md`](operations/rerank.md). Decisions where the design was silent:

- **Storage and API.** A singleton `rerank_settings` table like `systemone_settings` (model, `{candidates, timeLimitMs}`, revision; migration `00040_rerank`, which also widens the price units). `GET`/`PUT /v1/admin/rerank` (admins write with If-Match, auditors read; audited `platform.rerank_settings_update`) and `GET /v1/rerank/status` for editors. A rerank model in use can't be deleted; a disabled model or connection turns reranking off.
- **Admin → Models**: a notice above the list ("Reranking is off" or the model, candidates, time limit and how many published agents rerank) with **Reranking settings** opening a dialog; shown once a rerank model exists. Candidates 5–50 (default 40; a knowledge-base search returns at most 50), time limit 200–10,000 ms (default 2 s).
- **Agents.** `rerank` (default on; configurations saved before v0.4 are on) and `rerankTopN` (1–20, default 6). A reranked search keeps `rerankTopN` instead of the sum of the knowledge bases' top-k (a `search_knowledge` call's `maxResults` can ask for fewer); each knowledge base is searched for at least the candidate count. SystemOne judges the kept passages (at most its own candidate count). Reranking runs in the early search, alongside the input and scope checks, since the question has already gone to the embedding model.
- **Fail open.** An error or a call past the time limit keeps the fusion order and the usual results per search. The rerank model reads passages only up to its maximum classification: a search over a knowledge base above it (for an agent, any of its knowledge bases) isn't reranked (`skipped`).
- **What the reranker reads**: the passage's title, heading path and text; with a maximum input length set on the model, passages are shortened to fit with the question (4 characters per token).
- **Compatibility.** Requests send `top_n` and `return_documents: false`; flags `rerankDocumentsField` (`texts` for text embeddings inference) and `supportsRerankTopN`. Responses are read as `results` or `data` lists or a bare list, with `relevance_score` or `score`.
- **Retrieval API, Try it, MCP.** `rerank: false` on `/retrieve` compares with the fusion order; hits carry `rerankScore` and the result `rerank {status, candidates, latencyMs}`. MCP `search` reranks but its output is unchanged.
- **Evaluations** (cheap, so built): `rerank: false` when starting a run; the run's configuration records `rerank` `on` or `off` (absent without a rerank model) and the chart marks a change. An agent set's reranked retrieval run uses its `rerankTopN` as k.
- **Metering.** `rerank_tokens` (the server's count, else an estimate: the question with each passage, 4 characters per token) and `rerank_requests` per answered call, priced per rerank model; a new spend category `rerank` (also a CSV column before `tokens`). The cost chart has six tones, so Rerank shares Embedding's colour (both are retrieval); the legend and table name them apart.
- **Health.** Test model scores a passage that answers a fixed question against one that doesn't and fails when the second wins; the scheduled check derives rerank models' health from the connection's model list, as for other models.
- **Observability.** `grounded_rerank_requests_total{caller, status}`, `grounded_rerank_duration_seconds{caller}` (callers `agent`, `retrieve`, `evaluation`), a Reranking dashboard row, and `rerank` / `rerank <model>` spans with counts only.
- **Deferred:** a content-free per-answer rerank record in `message_events` and analytics tiles (the metrics and usage events cover it for now); rerank scores in MCP `search` output; reranking MCP tool results; a seventh chart tone in bitop-ui.

## 4. Public answers streamed while they're moderated

Today an answer under buffered moderation (the default for public agents) is written whole, checked, then sent: visitors wait 5–10 s for anything. Instead the answer is released in **checked chunks** as the model writes it: nothing reaches a visitor unchecked, and moderation still fails closed (a failing or unavailable check withholds the rest).

### Owner decisions (2026-09-30)

1. ~~Chunk size?~~ **Paragraph by paragraph.** Text is held until a paragraph ends (a blank line, or a length limit for very long paragraphs); the answer so far is checked as a whole (so context counts), then the new paragraph is released. About 3–6 checks per answer; first words after roughly 2–4 s.
2. ~~A later paragraph fails?~~ **The whole answer is replaced by the moderation notice** (as stream-then-retract does today), and it's stored as withheld.
3. ~~With the existing modes?~~ **A third output mode, "Stream checked paragraphs", the new default for the Public audience.** Buffer and Stream, then retract stay available (Admin → Safety → Moderation, and agents' overrides); a Public policy an admin has saved keeps its mode, an unsaved one gets the new default.

### How it gets built

1. The moderation policy gains the output mode `stream_checked` (validated like the others); `DefaultPolicy` for Public uses it. No migration: saved policies keep their mode.
2. The chat pipeline: a chunker on the model's text (a paragraph ends at a blank line, or at about 800 characters at a sentence end), each chunk checked with everything before it while the model keeps writing; chunks released in order; a failing check retracts with the notice (the `moderation` event) and stores the answer as withheld; an unavailable provider fails closed per the policy. Thinking is never shown in this mode.
3. Events: the stream says which mode it's in; the UI shows the steps until the first paragraph, then follows the answer as it grows (the buffered "show from its start" behaviour stays for Buffer).
4. Metering of the extra moderation calls, a metric for the time to the first released paragraph, tracing spans per check.
5. Tests with a fake moderation provider (a pass, a fail in paragraph 3, an outage, a very long paragraph, the citation check after the last chunk), the widget and the public page, docs.

### As built (M5, [`moderation-streaming.md`](moderation-streaming.md))

`moderation.ModeStreamChecked`, the default of an unsaved Public policy (no migration: a saved policy keeps its mode); `internal/agents/streamcheck.go` (the chunker, the checks, the release); `message_start.mode`; Admin → Moderation's third **Answers** option; the agent's Safety override. Where the design was silent:

- **Paragraphs.** A chunk ends at the last blank line in the held text; without one, once it reaches 800 characters, at its last sentence end (`.`, `!` or `?`, with closing quotes, brackets, emphasis or `[n]` markers, before a space; or a line end); with no sentence end, at the last space once it reaches 1,600. Held text that is only white space waits for the next paragraph, and trailing white space is released unchecked.
- **One check in flight.** The checks run in one goroutine per answer, in order, from a queue the model's text fills without waiting, and that goroutine releases each paragraph (the stream's events are serialised by a mutex). The final remainder is queued when the model ends, and the answer waits for the queue before `message_end`. Checks outlive a client that left (like the output check), so the stored answer is moderated.
- **The last check is the whole-answer check.** No extra check runs at the end: the last paragraph's check reads the whole text. The record keeps one decision (the failing one, else the strongest: error, flag, pass; the latest among equals) and `checks`, the number of checks.
- **Failing.** The `moderation` event goes out as soon as a check fails (`retracted` when paragraphs were shown, `withheld` when none were, `unavailable` or `support` as usual); later text is dropped. The model isn't stopped: an interrupted stream reports no token usage, so stopping it would under-meter the answer. The stored code stays `moderation_withheld` (or `moderation_unavailable`, `moderation_support`); the gap report and the answer cache skip it like other moderated answers.
- **Only streams are chunked.** A JSON answer, the non-streamed OpenAI-compatible call and MCP `ask` are checked once, whole (nobody sees text early). A saved answer's replay is one `text_delta`, never checked again; its `message_start` has no mode (moderation isn't planned on an exact hit).
- **Citation checks** run after `message_end`, as for streamed answers (`citationTiming` is `checkAfter` for any mode but buffer), so chips and claims arrive with `citations_checked`; on the OpenAI-compatible stream they're annotate-only, as for streamed answers.
- **The agent override** is a radio group, "Check answers before showing them": *As the platform's policy says* (`""`), *Paragraph by paragraph* (`stream_checked`) and *The whole answer* (`buffer`), replacing the buffer switch. Merging takes the stricter of the platform's and the agent's (stream then retract < checked paragraphs < buffer).
- **The UI.** `message_start.mode` (`stream_retract`, `stream_checked`, `buffer`, absent without output moderation) sets `checked` on the answer; "Writing and checking the answer…" shows until its first paragraph, then the answer follows the bottom as it grows. `buffered` stays for buffer mode only, so "show from its start" is unchanged.
- **Observability.** `grounded_moderation_first_release_seconds{channel}` and `grounded_moderation_paragraph_checks_total{decision}` (two panels in the Moderation row of the Models & moderation dashboard), and a `moderation.paragraph` span per check (its number, the characters checked, the decision). Metering needed nothing new: every answered check is a `moderation_requests` unit, or SystemOne tokens.
- **Deferred:** stopping the model after a failure with an estimated usage; a per-agent paragraph size.

## 5. Document viewer with highlights (B10) and citation marks per claim (A13)

A citation opens its passage, highlighted, in its document: the clearest proof that an answer is grounded. And each citation mark shows the verdict of the claim it supports, not the worst verdict of every sentence that cites the same source.

### Owner decisions (2026-09-30)

1. ~~What does a citation open?~~ **The cited passage in context for everyone who can chat; the whole document for the team's editors, admins and owners.** The context is the passage with its neighbours (about a page) under the document's title and heading path; web pages also offer "Open the page" with a text fragment that highlights the quote on the live site. Nobody can page through a knowledge base by its answers.
2. ~~Where does it open?~~ **A side panel beside the answer** (a split view like the agent editor's Try it, not an overlay drawer); a full-screen sheet with a close button on phones. The other sources stay one click away.
3. ~~Per-claim verdicts?~~ **A breakdown:** a source card reads "Supports 3 claims · 1 not supported" (in the verdict colours) instead of the worst verdict of every claim citing it; the viewer lists each claim that cites the passage, with its verdict, beside the highlighted passage.

### How it gets built

1. API (OpenAPI first, authorization matrix): a cited passage in context (the passage, its neighbours, title, heading path, URL, and the claims citing it in that answer) for anyone who may read the conversation (the asker, an anonymous session for its own conversation); the whole document's text for the team's editors, admins and owners. Answers only expose passages they cited.
2. The side panel (a split view beside the conversation; a full-screen sheet on phones): highlighted passage, context, "Open the page" with a text fragment for web pages, "Open full document" for editors, the claims with their verdicts; opened by "Show source", a source card or a marker. Keyboard and screen-reader friendly; axe clean.
3. Source cards: the per-claim breakdown instead of the worst verdict (the chat, Try it, the public page, the widget).
4. Tests (who may open what, an anonymous visitor's own conversation only, a passage deleted since the answer), docs.

### As built (M3)

User and operator guide: [`source-viewer.md`](source-viewer.md). Decisions where the design was silent:

- **API.** `GET /v1/messages/{messageId}/sources/{n}` (the asker; a personal key with the `query` scope, like the conversation) and `GET /v1/public/agents/{agentId}/messages/{messageId}/sources/{n}` (the anonymous session's own conversations; under `/v1/public` for the session cookie's path) return a `CitedPassage`: `status` (`available`, `document_deleted`, `passage_changed`), title, heading path, the citation's link, the passages with the cited one marked, the claims citing it, and `documentTeam` when the caller may open the whole document. Platform admins under break-glass get 404: break-glass's conversations scope covers transcripts, not document text. A message ID is enough (like feedback); `n` is the stored number. MCP tools' results are not passages (404).
- **Finding the passage.** Citations now carry `chunkId`. A passage is found by ID while it is one of its document's current passages (its source's embedding profile), else by its text (the stored snippet), which also serves answers from before v0.4.0; otherwise `passage_changed`. A document whose row is gone is `document_deleted`. Whether the document's source is still attached to the agent isn't checked again: the answer already showed the passage.
- **"About a page".** The cited passage plus neighbours on each side until about 1,200 characters, at most 3 a side (at least one when there is one). Text a passage repeats from the one before it (chunk overlap) is left out; the cited passage is always whole (the one before it loses the repeated tail).
- **Whole documents.** `GET /v1/teams/{team}/sources/{sourceId}/documents/{documentId}/text` (`?from=&limit=`, up to 200 passages; or `?around={chunkId}`): team editors, admins and owners and keys acting as editors (`ingest`, `manage`), and break-glass's documents scope (it already reads passages); members get 403. Data sources lets members read documents, but the owner's decision limits whole documents to editors and above. Platform-shared sources' documents show the passage in context only (they belong to no team). Try it and the widget preview store nothing, so their viewer reads passages through this endpoint with `around`.
- **"Open the page"** only when the citation has a URL (the agent's citation mode links sources), so the viewer never reveals more than the answer did. The text fragment is built in the browser from the cited passage's words (Markdown, list markers and table pipes removed): the whole passage when it has at most 8 words, else its first 4 and last 4 (`#:~:text=start,end`, with `-`, `,` and `&` encoded).
- **Layout.** A resizable split (bitop-ui's Resizable) beside the conversation when the chat is at least 720 px wide, one above the other when narrower (Try it), and a full-screen bottom sheet below 40rem (phones, and the widget's frame). The split is always mounted, so opening a source doesn't remount the conversation. Focus goes to the viewer's title, Escape closes it, and focus returns to what opened it, or to the source's card when that was a chip's card (which closes as it goes).
- **Openers.** A chip's card action reads "Show source n" and opens the viewer (and the sources under the answer); a source card is a button that opens it, with the web page as a separate "Open the page" link. Where there is no viewer (a transcript of a deleted agent, evaluation runs), chips keep "Show source n below".
- **Source cards.** "Supports 3 claims · 1 not supported" counts this source's check of each claim citing it (verified, unsupported, contradicted, and "not checked" apart); when it supports none, the first part names the claims ("1 claim not supported"). Cards of answers checked before v0.2.1 keep the source's own verdict.
- **bitop-ui.** `Sheet` gained `size="full"` and `Source` gained `onSelect` (with `selectLabel` and `linkLabel`): generic, so they went into bitop-ui rather than app code.
