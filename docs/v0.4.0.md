# v0.4.0: answers people trust and teams can improve

Status: **being designed** (owner, 2026-09-30). The scope and its order are in [`roadmap.md`](roadmap.md) § K: the unanswered-questions and gap report (C2, A15), cross-encoder reranking (A1b), an answer cache (A8), public answers streamed while they're moderated, and a document viewer with highlights with citation marks per claim (B10, A13). Each gets a section here before it's built; decisions are recorded as they're made.

## 1. Answer cache (A8)

A question that was answered recently, under the same conditions, gets the stored answer again instead of the whole pipeline (rewrite, search, SystemOne judging, the model, citation checks, buffered moderation): well under a second, at no model cost, with the same citations and claim verdicts as the original.

### When an answer is reused

All of these must hold:

- **The same published agent version.** Publishing a version (model, instructions, knowledge bases, settings) starts a fresh cache.
- **The same knowledge.** Each knowledge base gets a `content_revision`, raised whenever a document is added, changed, re-crawled or deleted, or the knowledge base moves to another embedding profile. The cache key includes the revision of every knowledge base the agent uses.
- **The same answering settings:** a settings revision covers the platform's and the agent's moderation and SystemOne settings.
- **The same question.** By default the match is **exact** after normalising (case, whitespace, trailing punctuation). Optionally (decision 1), a **near-identical** question matches too: the nearest cached question by embedding, above a high similarity, confirmed by SystemOne as asking the same thing, so "hours on Saturday" never gets "hours on Sunday".
- **A question that stands on its own:** the first message of a conversation, or a follow-up that doesn't lean on the conversation (`needsContext`, as for the query rewrite).
- **A clean answer:** passed moderation, no error, not refused because of a failure, and no thumbs-down since.
- **No MCP tool results:** tools return live data, so an answer that used one is never cached.
- **Not expired:** a per-agent time limit (decision 3).

Evaluations and Try it never read or write the cache.

### What a cached answer still goes through

The chat's limits (rate limits, query limits, budgets, concurrent chats), the conversation and message records (the message is marked `cached`), the audit and usage records (zero model tokens, channel as usual), and the same streamed events as a live answer (so the web chat, the widget, the public page, the OpenAI-compatible API and MCP need no changes). A thumbs-down on a cached answer removes the entry, so the next person gets a fresh one.

### Storage and lifetime

An `answer_cache` table in Postgres (shared by every pod, kept across restarts, a lookup by key in about a millisecond): agent version, normalised question and its hash, the knowledge-base revisions and settings revision of the key, the answer (text, citations, claims, sources), created, expires, hits, last hit. Cached answers follow the agent's retention rules and data classification like messages; a periodic job deletes expired entries. Editors can **clear an agent's cache** (Agent → Settings), and a platform admin can turn the cache off for the whole platform.

### Owner decisions (2026-09-30)

1. ~~Matching?~~ **Exact by default, with an option to also match near-identical questions confirmed by SystemOne** (per agent; needs a SystemOne model).
2. ~~Default?~~ **On by default for public agents; every agent has its own on/off setting** (Agent → Settings), whatever its audience.
3. ~~Expiry?~~ **24 hours by default**, configurable per agent.
4. ~~Visible to people?~~ **Invisible**: no "saved answer" note and no "ask again" in the chat. A stale answer goes away with the time limit, a thumbs-down, a change to the agent or its knowledge, or an editor clearing the cache. The audit and usage records and the agent's analytics (a cache-hit rate and the tokens saved) still show it.

### How it gets built

1. A migration: the `answer_cache` table, `content_revision` on knowledge bases (raised by ingestion, deletion and profile switches), a settings revision.
2. The cache service: normalising, eligibility, lookup and store, near-identical matching with the SystemOne check, eviction, the expiry job.
3. The chat pipeline: look up right after the limits are admitted; on a hit, replay the stored answer's events; on a miss, answer as today and store the answer if it qualifies.
4. API (OpenAPI first) and UI: the agent's cache settings (on/off, near-identical, time limit) and **Clear cache**, the platform switch, `cached` on messages, a cache-hit tile in agent analytics. Everything in the authorization matrix.
5. Tests for hits, misses and every invalidation above; metrics (hit rate, tokens saved); docs.

## 2. Unanswered-questions and gap report (C2, A15)

Teams see what their agents fail at, grouped into topics, so they know what to add: "14 questions about parking permits got no answer this month" → add the parking page to the knowledge base.

### What counts as a failed question

Already recorded per answer (`message_events`, without content): **no context** (the search found nothing), a **strict refusal**, every passage **judged out** by SystemOne, **out of scope** (the scope check), a **thumbs-down** with its reason (`missing_sources`, `outdated`, `incorrect`, `wrong_sources`…), and unsupported or uncited claims. A question answered well later (for example after a source was added) closes its topic.

### The privacy question

ADR-0010: transcripts belong to the user; teams see aggregates and metadata only, never content or who asked. A report of *topics* needs the question text (or at least its meaning), so this changes ADR-0010 in some way. Options:

- **A. Counts only** (no change): failures by signal, agent, day and cited documents. No topics, so it can't say *what* to add.
- **B. Topics with a minimum crowd** (a small change): failed questions are kept apart from transcripts, embedded and grouped into topics; a model writes each topic's short label ("Parking permits"); teams see the label, the count, the signals and the trend, **never a question's text or who asked**, and a topic shows only once at least 3 different people asked about it (so a label can't point at one person). The stored questions follow the transcript retention and are deleted with their conversation.
- **C. B, plus shared questions** (A15): on a thumbs-down, the person may tick "share this question with the team" (off by default); shared questions show in full under their topic, can be added to an evaluation set in one click, and also count towards topics.
- **D. Show failed questions in full** to editors, with a notice to users: the most useful, the biggest change to ADR-0010.

### Still to decide (after the privacy model)

Who sees the report (editors, admins, owners; platform admins across teams?), how topics are formed and labelled (embedding clusters + a chat or SystemOne label), how often they're rebuilt, the actions on a topic (dismiss, mark fixed, add a source request, add to an evaluation set), notifications (a weekly digest?), and public agents' anonymous visitors.

### Owner decisions (2026-09-30)

1. ~~Privacy model?~~ **C: topics with a minimum crowd, plus questions shared on a thumbs-down.** Failed questions are kept apart from transcripts and grouped into labelled topics; teams see a topic's label, count, signals and trend, never a question's text or who asked, and only once at least 3 different people asked. On a thumbs-down, the person may tick "Share this question with the team" (off by default): a shared question shows in full under its topic and can be added to an evaluation set. ADR-0010 is amended accordingly.
2. ~~Who sees it?~~ **A team's editors, admins and owners** (on the team, alongside Evaluations and Agent → Analytics). Members don't; platform admins and auditors see counts only (failed questions per team and signal), never topics or shared questions.
3. ~~Topics and labels?~~ **Embedding clusters, labelled by the chat model.** Each failed question is embedded with the agent's embedding profile; a worker job regroups them hourly; once a topic has at least 3 different askers, the team's chat model writes its 2–5 word label from the topic's questions. The label is the only text shown for a topic without shared questions.
4. ~~Actions on a topic?~~ **Act on it, then let it close itself:** Add a source (Data sources, with the topic as a note), Add to evaluations (its shared questions), Dismiss (optional reason) and Mark fixed. A dismissed or fixed topic reopens on new failures; a topic closes itself when its questions start being answered well. Audited. No digest for now.
5. ~~Public agents' anonymous visitors?~~ **Included, each anonymous session counting as one person.** Their failed questions are kept as long as other failed questions (the agent classification's transcript retention), never linked to a visitor; the public page's footer adds that questions that can't be answered may be grouped, without the visitor's details, to improve the agent.

### How it gets built

1. **ADR-0010 amendment** (done with this design): failed questions and shared questions.
2. **Migration:** `gap_questions` (team, agent, the question's text and embedding, the signals, a pseudonymous asker key, shared or not, created; deleted with its conversation and by retention), `gap_topics` (team, agent, label, state open/dismissed/fixed, counts, first and last seen, reasons), and the link between them; a `shared` flag on feedback.
3. **Capture:** when an answer fails (the signals above) or gets a thumbs-down, the chat pipeline records its question (already embedded for the search, so no extra model call); a shared question is marked on a thumbs-down.
4. **Topics job** (worker, hourly): clusters each agent's open questions by similarity, keeps topics stable between runs, labels those reaching 3 askers with the chat model (metered as the team's spend), closes topics whose questions are now answered well, reopens on new failures, and prunes by retention.
5. **API** (OpenAPI first, authorization matrix): topics per team and agent with counts and trend, a topic's shared questions, the four actions, the share tick on feedback; counts per team for platform admins and auditors.
6. **UI:** a **Gaps** view (team, beside Evaluations; and per agent in Analytics), topic rows with signals and trend, a topic page with shared questions and the actions, the share tick in the thumbs-down form, the public footer line.
7. Tests (the 3-asker minimum, deletion with conversations, retention, reopening, permissions), metrics, docs.

## 3. Cross-encoder reranking (A1b)

A reranking model (a cross-encoder, called through the gateway's `/rerank` endpoint as LiteLLM, vLLM and SGLang serve it; for example bge-reranker or Qwen3-Reranker) reads the question with each candidate passage and scores how well the passage answers it: more precise than the vector and keyword fusion, in one batched call. The `rerank` model kind already exists in the catalog; nothing uses it yet.

### Owner decisions (2026-09-30)

1. ~~With SystemOne judging?~~ **Rerank first, then judge only the best few.** The search fetches about 40 candidates; the reranker scores them in one call; SystemOne judges only the top few (instead of 10–20); without SystemOne, the top-ranked passages go to the model.
2. ~~Where is it set?~~ **A platform rerank model, on by default, with each agent able to turn it off.** Admin → Models chooses the rerank model (like the SystemOne model); once chosen, every agent, the knowledge-base Try it, the REST retrieval API and MCP `search` rerank. An agent can turn it off and set how many top passages to keep (Build → Advanced, default 6). Without a rerank model, retrieval is as today.

### How it gets built

1. The gateway client's `/rerank` call (Cohere/Jina request shape, as LiteLLM, vLLM and SGLang accept it), compatibility flags for servers that differ, a connection Test and stored health for rerank models.
2. The platform setting (the rerank model, like the SystemOne model) and the agent's `rerank` and `rerankTopN` config fields (OpenAPI first; a migration only if settings need a column).
3. Retrieval: fetch about 40 candidates, rerank them in one call, keep the top N for judging or the model; **fail open** (a rerank error or timeout keeps today's fusion order, with a time limit like passage judging's); the score shown in Try it and the retrieval API.
4. Metering (`rerank` requests and tokens, priced like other units), tracing spans, metrics, evaluations comparing runs with and without reranking.
5. Tests with a fake `/rerank` endpoint in the fake gateway; docs (operators: deploying a reranker; editors: the agent setting).

On the reference install, a rerank model has to be deployed on the gateway first.

## 4. Public answers streamed while they're moderated

Today an answer under buffered moderation (the default for public agents) is written whole, checked, then sent: visitors wait 5–10 s for anything. Instead the answer is released in **checked chunks** as the model writes it: nothing reaches a visitor unchecked, and moderation still fails closed (a failing or unavailable check withholds the rest).

### Owner decisions (2026-09-30)

1. ~~Chunk size?~~ **Paragraph by paragraph.** Text is held until a paragraph ends (a blank line, or a length limit for very long paragraphs); the answer so far is checked as a whole (so context counts), then the new paragraph is released. About 3–6 checks per answer; first words after roughly 2–4 s.
2. ~~A later paragraph fails?~~ **The whole answer is replaced by the moderation notice** (as stream-then-retract does today), and it's stored as withheld.
3. ~~With the existing modes?~~ **A third output mode, "Stream checked paragraphs", the new default for the Public audience.** Buffer and Stream, then retract stay available (Admin → Safety → Moderation, and agents' overrides); a Public policy an admin has saved keeps its mode, an unsaved one gets the new default.

### How it gets built

1. The moderation policy gains the output mode `stream_checked` (validated like the others); `DefaultPolicy` for Public uses it. No migration: saved policies keep their mode.
2. The chat pipeline: a chunker on the model's text (a paragraph ends at a blank line, or at about 800 characters at a sentence end), each chunk checked with everything before it while the model keeps writing; chunks released in order; a failing check retracts with the notice (the `moderation` event) and stores the answer as withheld; an unavailable provider fails closed per the policy. Thinking is never shown in this mode.
3. Events: the stream says which mode it's in; the UI shows the steps until the first paragraph, then follows the answer as it grows (the buffered "show from its start" behaviour stays for Buffer).
4. Metering of the extra moderation calls, a metric for the time to the first released paragraph, tracing spans per check.
5. Tests with a fake moderation provider (a pass, a fail in paragraph 3, an outage, a very long paragraph, the citation check after the last chunk), the widget and the public page, docs.

## 5. Document viewer with highlights (B10) and citation marks per claim (A13)

A citation opens its passage, highlighted, in its document: the clearest proof that an answer is grounded. And each citation mark shows the verdict of the claim it supports, not the worst verdict of every sentence that cites the same source.

### Owner decisions (2026-09-30)

1. ~~What does a citation open?~~ **The cited passage in context for everyone who can chat; the whole document for the team's editors, admins and owners.** The context is the passage with its neighbours (about a page) under the document's title and heading path; web pages also offer "Open the page" with a text fragment that highlights the quote on the live site. Nobody can page through a knowledge base by its answers.
