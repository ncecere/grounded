# Dependencies, SBOM and scan results

## The SBOM

Every image published by CI (`.github/workflows/image.yml`, on pushes to `main` and `v*` tags) is built by BuildKit with `sbom: true` and `provenance: mode=max`. The SBOM (SPDX, generated by BuildKit's Syft scanner) and the SLSA provenance are attached to the image in the registry as attestations, for each platform. The image is then scanned by Trivy and signed with cosign (keyless, bound to the workflow's identity).

Read them for an image digest:

```sh
IMAGE=ghcr.io/ncecere/grounded@sha256:...
docker buildx imagetools inspect "$IMAGE" --format '{{ json (index .SBOM "linux/amd64").SPDX }}' > sbom.spdx.json
docker buildx imagetools inspect "$IMAGE" --format '{{ json (index .Provenance "linux/amd64").SLSA }}' > provenance.json
cosign verify "$IMAGE" \
  --certificate-identity-regexp '^https://github.com/ncecere/grounded/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

Since v0.2.0 each GitHub Release also carries them as files (`deploy/release/github-release.sh`): `grounded-<tag>-<os>-<arch>.sbom.spdx.json` for each platform, `grounded-<tag>.digest.txt` (the image reference by digest) and `checksums.txt` (SHA-256 of both; `sha256sum -c checksums.txt`). They are copies of the attestations of the digest the release names; the attestations remain the signed source.

The SBOM covers the whole image: the Go modules compiled into `/grounded` (read from the binary's build information), the web UI's packages as bundled, and the distroless base's Debian packages.

### The OCR image's base

`grounded-ocr` is Debian with Tesseract and its libraries (`Dockerfile.ocr`); the `grounded` image is distroless and has one finding. **Since v0.4.4 the base is Debian 13 (trixie) instead of Debian 12**, which took the scan from 415 findings to 327 and the critical ones from three (`libglib2.0-0` CVE-2026-58016, `libxml2` CVE-2026-6653, `zlib1g` CVE-2023-45853) to one: **`libxml2` CVE-2026-6653**. Tesseract is 5.5.0 instead of 5.3.0; on six synthetic pages (three fonts, clean and scan-like) the two engines read identically, at a 3.26% character error rate each. All 327 findings are in Debian packages that Debian has not fixed, so the CI gate (Trivy on every published image, failing on fixable HIGH and CRITICAL findings) passes and an upgrade cannot remove them. The packages with the most high or critical findings are `libxml2` (8), `libtesseract5` and `tesseract-ocr` (6 each), `libexpat1` (5) and the util-linux libraries (`bsdutils`, `libblkid1`, 4 each).

**Which findings a page image can reach (assessed 2026-10-14 on v0.4.4; it still holds for v0.5.0, whose findings are a subset and whose OCR inputs are unchanged, see the scan table).** The sidecar accepts only a body that starts with the PNG signature (anything else is a 415), writes it to a fixed path (`<temp dir>/page.png`), and runs `tesseract` on that path with a language name that is checked against the installed list (`cmd/grounded-ocr`). From that and from Tesseract 5.5.0's source:
- **`libxml2` (the one critical finding, CVE-2026-6653) is not reachable from an image.** Tesseract links `libarchive`, which links `libxml2`, but `libarchive` is used only in `TessdataManager::LoadArchiveFile`, to read a language data (`.traineddata`) file, never the image.
- **`libcurl` is not reachable from an image.** Tesseract uses it only when the image *filename* contains `://`; ours is always a local path.
- **The six high findings in `tesseract-ocr` and `libtesseract5`** (CVE-2026-73066, 88047, 88048, 88051, 88052, 88053) are all out-of-bounds or overflow bugs in parsing a **crafted `.traineddata` model** (LSTM layers, normalization prototypes, integer templates, the unicharset). They need an attacker who can put a model file in the tessdata directory, which the shipped image takes from Debian packages on a read-only filesystem, run as non-root. A derived image that adds its own language files takes that risk on itself.
- **The four high findings in `libmount1` (util-linux) are not reachable:** `tesseract` does not link it, and the service never runs a mount helper (non-root, no capabilities).
- **What an image does reach** is `libpng`, `zlib`, Leptonica and the C and C++ runtimes. In those packages the scan lists no high or critical finding (two low in `libpng`, two medium in `zlib`, and medium or low in `libc6`, `libstdc++6`, `libgcc-s1` and `libgomp1`).

**What this does not show.** It covers the findings Trivy knows today; an unknown flaw in `libpng` or Leptonica is possible in any image that decodes images. It rests on the sidecar keeping the PNG check, the fixed path and the language check: a change that passes a URL, an archive or a caller's model file to Tesseract would make the findings above reachable. Until Debian fixes them, the base-image findings stay in scans; the shipped component limits what the service can do (non-root, all capabilities dropped, read-only root filesystem, a seccomp profile, no service account token, and a NetworkPolicy that lets only the API and the worker reach it). In v0.6.2 and earlier the OCR policy restricted ingress only. The unreleased hardening in [#77](https://github.com/ncecere/grounded/issues/77) also isolates egress and excludes OCR from the base DNS grant: policies combine by union, so the old namespace-wide DNS allow would otherwise defeat OCR's own restriction. The [real NetworkPolicy acceptance test](../../deploy/kubernetes/test/ocr-networkpolicy.md) checks standalone and composed policies with positive controls, API/worker access and fresh readiness probes; operators adding broader allow policies must exclude OCR to retain isolation. Do not expose the OCR service outside the namespace.
