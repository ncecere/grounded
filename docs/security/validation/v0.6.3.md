## Upgrade rehearsal and migration repair

The first release review found that the original 00054 migration was not staged:
it added a stricter unique index that v0.6.2 writers did not recognize. A
Unicode-only name collision could become 500 on an old pod during rollout.
[#195](https://github.com/ncecere/grounded/issues/195) blocked release until #196
repaired it. The extended harness reproduces that 500 on the unrepaired image.

The repaired application image built from `cd60606` passed the v0.6.2 upgrade
rehearsal on a disposable C-locale PostgreSQL 17 database. Besides source,
conversation, retrieval, API-key and chat checks, it verifies:

- template saves and renames by the old image after the new migration;
- new-code Unicode-twin refusals as 409 with unchanged rejected records;
- approvals with changed classification before and after migration, read correctly
  by the new version; and
- old and new writers running alongside each other.

The parent found a harness assumption that would fail once the repaired code
became the old baseline. The original harness fails that replay; the corrected
harness passes with **both v0.6.2 and the repaired code as old baselines**, recording
the old writer's pre-migration 201/409 behaviour and requiring it afterward.
Unexpected feature-probe errors fail, rather than skip coverage. All rehearsal
containers, networks and blob volumes were removed.

Schema 54 now renames existing duplicate template names and adds a **non-unique**
lookup index. New writers enforce the folded-name rule under an advisory
transaction lock; the stricter unique constraint is deferred to a later release.
Schema 55 only adds a constant-default column: it performs no table-wide backfill.
Legacy approvals resolve through the indexed audit lookup. See
[staged constraints](../../operations/upgrades.md#staged-constraints), including
ICU requirements and the temporary legacy behaviour of old writers.
